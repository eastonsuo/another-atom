## 2. 本地启动

### 2.1 前置条件

- Python 3.12 及以上；
- [uv](https://docs.astral.sh/uv/)；
- Node.js 22 及以上；
- npm。

### 2.2 安装依赖

在仓库根目录执行：

```bash
uv sync --dev
cd studio
npm install
npm run build
cd ..
```

`npm run build` 会把 React Studio 产物写入 `studio/dist`，FastAPI 将其作为同域静态页面提供。

### 2.3 启动独立执行服务与主服务

先在一个终端启动共享独立执行服务：

```bash
uv run uvicorn another_atom.executor.app:app --host 127.0.0.1 --port 8001
```

再在另一个终端启动主服务：

```bash
uv run uvicorn another_atom.main:app --host 127.0.0.1 --port 8000
```

浏览器打开：

- Studio：<http://127.0.0.1:8000>
- API 文档：<http://127.0.0.1:8000/docs>
- 健康检查：<http://127.0.0.1:8000/api/health>
- 管理员后台：<http://127.0.0.1:8000/admin/login>（开发默认 `admin / admin12345`）

本地默认数据库是 `data/another_atom.db`。停止服务后再次启动，已有项目和版本仍会保留。需要干净数据时，先停止服务，再删除该数据库文件。

### 2.4 配置真实模型与 DeepSeek 兜底

仓库提交的 `.env.example` 只包含空的 Secret 占位符。本地 `.env` 被 Git 忽略，可以按以下方式配置：

```text
LLM_PROVIDER=ollama
OLLAMA_API_KEY=<Ollama Cloud Key>
OLLAMA_HOST=https://ollama.com
OLLAMA_MODEL=deepseek-v4-flash
OLLAMA_VISION_MODEL=qwen3.5:397b
VISION_TIMEOUT_SECONDS=120
OLLAMA_TIMEOUT_SECONDS=120
OLLAMA_LEAD_TIMEOUT_SECONDS=60
OLLAMA_FAILOVER_TIMEOUT_SECONDS=30
DEEPSEEK_API_KEY=<轮换后的 DeepSeek 官方 Key>
DEEPSEEK_HOST=https://api.deepseek.com
```

- **正常路径：** 所有结构化角色调用优先使用 Ollama Cloud；Lead 关闭 thinking，减少简单路由的延迟。
- **触发条件：** 只有 Ollama 请求超过 `OLLAMA_FAILOVER_TIMEOUT_SECONDS` 才切换一次 DeepSeek 官方 API。普通 HTTP 4xx/5xx 或 Schema 校验失败不会伪装成超时兜底。
- **可见状态：** Lead 等待超过阈值时显示“服务商切换中”；Run 内角色成功切换后持久化 `provider.fallback` 事件。
- **结算方式：** Ollama 已发起的请求与 DeepSeek 官方请求都计入同一次阶段实际用量；剩余预占仍按阶段结算规则释放。
- **未配置时：** `DEEPSEEK_API_KEY` 为空则完全禁用官方兜底，Ollama 按原超时和失败路径返回错误。

Key 不得提交到 Git。曾经出现在聊天、日志或截图中的 Key 应先在服务商侧轮换，再写入本地 `.env` 或 Railway Secret。

### 2.5 配置管理员后台

开发环境启动时会初始化管理员 `admin / admin12345`，密码只以 PBKDF2 哈希存入数据库。公开演示允许保留默认账号，但服务会记录 `default_admin_credentials_active` 告警；正式对外使用建议在 Railway Variables 中覆盖：

```text
ADMIN_USERNAME=<管理员用户名>
ADMIN_PASSWORD=<独立强密码>
ADMIN_DISPLAY_NAME=<管理员显示名称>
SESSION_COOKIE_SECURE=true
```

服务重启时会将这组变量同步到数据库中的恢复管理员账户，但不会降级由后台显式提升的其他管理员。普通注册用户不能提升自己；只有已认证管理员可以通过后台把指定普通用户提升为管理员。生产环境未设置 Secure Cookie 时会记录 `session_cookie_secure_disabled` 告警。

### 2.6 本地试用路径

1. 在 Home 输入任意产品需求，例如扫雷游戏、计算器、看板或商品目录。
2. 选择 `Team` 和当前可用模型，点击右侧构建按钮。模型在 Run 创建后固定，不受后续切换影响。
3. 检查产品经理（Product Manager）生成的产品规格（ProductSpec）。产品经理必须保留原始产品目标；`supported` 和 `adapted` 都等待用户确认，`adapted` 还必须展示不可用的服务端或外部能力，`unsupported` 停止构建。用户也可显式要求产品经理重新生成需求草案。
4. 确认产品规格后，在左侧查看团队负责人、产品经理、架构师、工程师，以及运行系统（Runtime）的源码物化、构建、单元测试和确定性校验阶段事件。架构设计可检查但默认不增加第二次强制确认；只有它要求改变已确认产品边界时才退回产品规格重新确认。
5. 构建完成后切换 Desktop/Mobile，实际操作生成应用的按钮、状态和页面交互。
6. 在 `Edit` 修改标题、正文或主色并保存；确认版本列表新增一项。
7. 在 `Versions` 恢复旧版本；Restore 会创建新版本，不覆盖历史。
8. 点击 `Publish`，从提示条打开无需登录的公开路由。

产品接受任意软件需求；当前代码的可执行适配器以 Web 为主，通用源码可单独交付。下面专门检查“要求在平台实际运行、但适配器缺失”的边界，不代表非 Web 源码一律不能生成。本轮未核验以下功能的实际运行结果。可用以下输入检查“保留项目类型、明确 Adapter 缺口”的错误状态：

```text
Build and run a native iOS camera app online in this platform
```

结果应为 `unsupported`，原 Run 在构建前停止且不创建 Build Job。PM 必须保留原生 iOS 相机应用目标并说明当前缺少 iOS Build/Runtime Adapter，不能改成 Web 相机或商品目录。

```text
Build a CRM with real company login and cloud customer data
```

结果应为 `adapted`，Blueprint 保留 CRM 产品目标，同时列出真实登录和云端写入等未提供能力。

Mock 测试环境还保留显式失败标记：`[fail:llm]`、`[fail:build]`、`[fail:data]`。它们只用于验收错误状态，不是用户功能。

## 5. Railway 使用与部署

仓库已提供：

- 根目录 `Dockerfile`：构建 React Studio，并运行 FastAPI；
- `railway.toml`：指定 Dockerfile Builder、`/api/health` 健康检查和失败重启策略；
- SQLite 自动建表和单副本持久化逻辑。

Railway 会自动检测根目录中大写命名的 `Dockerfile`。参考：[Railway Dockerfile 文档](https://docs.railway.com/builds/dockerfiles)。

### 5.0 使用已有项目：CLI 入口

已有项目、环境、主服务与执行服务优先复用本地登记中的对象，读取路径和缺失时的处理见[环境登记规范](../agents/validation-environments.md)。下方 5.1–5.3 是首次创建时的步骤，不是每次部署都要重建资源。已有 CLI 登录可用时，不把 Railway MCP 作为查询的前置条件。

使用已登录身份；登录失效时通过 `railway login` 恢复，不读取认证缓存文件。下列命令按 CLI `5.26.0` 的帮助核对，后续差异以当前 `--help` 为准。测试用途可能对应独立 Project，也可能对应同一 Project 下的 Environment，不能把用途名称直接当作平台环境名。`railway environment list --json` 只查看当前关联项目，不能跨项目定位测试目标。

先从本地登记复制本次已确认目标的四个 ID；不同项目可能有同名环境或服务，不能混用 ID 或依赖上次关联的默认目标。以下占位符必须替换后才能执行：

```bash
AA_RAILWAY_PROJECT='<Project ID>'
AA_RAILWAY_ENVIRONMENT='<Environment ID>'
AA_RAILWAY_MAIN_SERVICE='<主服务 Service ID>'
AA_RAILWAY_EXECUTOR_SERVICE='<执行服务 Service ID>'

# 只读：核对目标身份、服务与活动部署。操作前重新读回，不依赖上次关联的默认环境。
railway status --project "$AA_RAILWAY_PROJECT" --environment "$AA_RAILWAY_ENVIRONMENT" --json

# 只读：分别查两个服务的版本记录，不能用主服务的版本推定执行服务。
railway deployment list --project "$AA_RAILWAY_PROJECT" --environment "$AA_RAILWAY_ENVIRONMENT" --service "$AA_RAILWAY_MAIN_SERVICE" --limit 5 --json
railway deployment list --project "$AA_RAILWAY_PROJECT" --environment "$AA_RAILWAY_ENVIRONMENT" --service "$AA_RAILWAY_EXECUTOR_SERVICE" --limit 5 --json

# 只读：核对执行服务的真实私网域名，不从服务职责或示例名拼接地址。
railway private-network status --project "$AA_RAILWAY_PROJECT" --environment "$AA_RAILWAY_ENVIRONMENT" --service "$AA_RAILWAY_EXECUTOR_SERVICE" --json
```

当前运行版本取匹配环境和服务的 `activeDeployments`，同时检查实例状态；`latestDeployment` 只是最新尝试，可能仍在构建或已经失败。必要的资源身份、实际入口与部署快照只保存在本地登记；提交的验证记录只引用用途别名和批次，不归档完整配置或敏感输出。

需要查日志时，先固定一个服务和部署 ID，再限制时间与数量，例如：

```bash
railway logs '<Deployment ID>' --project "$AA_RAILWAY_PROJECT" --environment "$AA_RAILWAY_ENVIRONMENT" --service "$AA_RAILWAY_MAIN_SERVICE" --since 15m --lines 100 --json
```

这只是查询模板，不表示已执行日志查询。不要用无边界流式日志代替一次查询，也不要为状态检查运行 `railway variable`、`railway shell` 或完整环境配置导出。`railway link`、`railway environment <name>` 和 `railway service link` 会改变本地默认目标，不是只读查看命令；已有 ID 时优先显式传参。

**触发部署前必须明确影响：** GitHub 源服务可以随绑定分支推送自动部署，这是 Railway 的[自动部署机制](https://docs.railway.com/deployments/github-autodeploys)。一个分支可能绑定多个项目或服务；推送前从本地登记及必要的只读核对确认全部影响范围，并记录自动部署开关、Watch Paths 与 Wait for CI 设置的已知值和未确认项。不能把分支推送视为只更新当前 CLI 关联目标，也不能默认纯文档提交会被忽略。

- 常规代码交付沿用现有 GitHub 源：固定本次提交与目标，确认推送可能影响的全部服务及授权，再推送。没有环境写入授权时，文档登记可以先本地提交，不用“只改文档”绕过部署边界。
- 只需重部署既有版本时，在已授权目标上使用 `railway redeploy --project <Project ID> --environment <Environment ID> --service <Service ID>`；它不同于 `--from-source` 拉取源的最新版本。执行前仍需核对重部署对象和可能生效的配置变化。
- `railway up` 会上传本地目录并触发部署，不等于部署当前 Git commit，也不是预检命令。只有用户选择本地上传路径且快照、目标和影响明确时才使用；不默认以它替代现有 GitHub 源，不使用 `--no-gitignore` 上传本地密钥文件。
- 平台受理、构建成功、活动实例运行、健康入口可达和功能验收通过分别读回。发生失败先保留必要证据；重启、回滚、清理、变量修改和环境创建不由一次部署授权自动推导。

### 5.1 从 GitHub 创建服务

1. 确认代码已经推送到公开或 Railway 有权访问的 GitHub 仓库。
2. 在 Railway Dashboard 选择 `New Project`。
3. 选择 `Deploy from GitHub repo`，授权 GitHub 后选择 `another-atom`。
4. 建议先选择添加变量或暂缓首次部署，先挂载持久化 Volume。

官方入口说明：[Railway Quick Start](https://docs.railway.com/quick-start)。

### 5.2 添加 SQLite 持久化 Volume

1. 打开 Another Atom Web Service 的 `Settings -> Volumes`。
2. 创建 Volume，并将挂载路径设为 `/app/data`。
3. 保持 Web Service 只有一个副本；多个副本不能共享同一个 SQLite 写入文件。
4. 打开 `Variables`，添加：

```text
DATABASE_URL=sqlite:////app/data/another_atom.db
LLM_PROVIDER=ollama
OLLAMA_API_KEY=<Railway Secret>
OLLAMA_HOST=https://ollama.com
OLLAMA_MODEL=deepseek-v4-pro
OLLAMA_VISION_MODEL=<Railway 中实际可调用的视觉模型标识>
VISION_TIMEOUT_SECONDS=120
OLLAMA_TIMEOUT_SECONDS=120
OLLAMA_LEAD_TIMEOUT_SECONDS=60
OLLAMA_FAILOVER_TIMEOUT_SECONDS=30
DEEPSEEK_API_KEY=<可选的 Railway Secret>
DEEPSEEK_HOST=https://api.deepseek.com
DEMO_QUOTA_UNITS=100
ENVIRONMENT=production
ADMIN_USERNAME=<管理员用户名>
ADMIN_PASSWORD=<独立强密码>
ADMIN_DISPLAY_NAME=<管理员显示名称>
SESSION_COOKIE_SECURE=true
```

`DEEPSEEK_API_KEY` 只在需要 Ollama 超时兜底时配置；未配置时不会发起官方 API 请求。Volume 是当前 Railway SQLite 部署的必要条件，否则重新部署或容器迁移后数据库文件可能丢失。参考：[Railway Volumes 文档](https://docs.railway.com/volumes)。

### 5.3 生成公网域名

1. 打开 Web Service 的 `Settings -> Networking`。
2. 生成 Railway Public Domain。
3. 将完整 HTTPS 地址写回 Web Service 变量，例如：

```text
PUBLIC_BASE_URL=https://<实际分配的公网域名>
```

4. 变量变更可能先形成待发布配置；按 Railway 当前界面审阅并部署后才算生效，不能把保存变量等同于已完成部署。部署后检查 `/api/health`。参考：[Railway 变量变更](https://docs.railway.com/variables)。

### 5.4 为什么必须保持单副本

SQLite 与本地 Project Git 都依赖当前实例挂载的 `/app/data`。这符合当前部署方案的 Railway 单副本边界，但不支持水平扩容。升级到多个 API/Worker 副本前，必须把业务状态迁移到 PostgreSQL，把共享 Artifact 迁移到对象存储，并补齐跨实例并发控制。

### 5.5 首次部署验收

按以下顺序检查：

1. Deployment Logs 出现 Uvicorn 启动成功，且没有数据库连接错误。
2. `https://<domain>/api/health` 返回 `status: ok` 和 `database: sqlite`。
3. 打开根地址，提交一个 `supported` 纯前端请求，确认产品规格进入等待确认；用户确认后才进入架构和工程阶段。
4. 刷新页面后重新打开项目，确认 Run、事件和版本仍存在。
5. Publish 后用无登录的隐身窗口打开 Public URL。
6. 执行 Unpublish，确认旧 Public URL 返回不可用状态。

如果健康检查通过但页面构建后卡住，先看主服务日志中的构建任务（BuildJob）状态，再看执行服务日志中的请求、源码物化、构建、测试和校验事件。主服务仍负责持久化调度，真实工程验证由独立执行服务完成。

### 5.6 共享独立执行服务的装配与验收

目标拓扑是在同一已确认 Railway 项目和环境中设置共享执行服务，与主服务使用同一代码库、不同 Dockerfile 和不同进程。实际服务名称与 ID 从本地登记读取，规则见[环境登记规范](../agents/validation-environments.md)；不要因为实际服务名与示例不同就重复创建。私网调用、认证与工程验收仍需单独验证：

1. 执行服务不生成公网域名，不挂载持久化卷（Volume），不配置数据库、模型服务、Git 和发布密钥。
2. 主服务通过登记中实际读回的私网 DNS、经核对的监听端口和共享服务令牌调用执行接口。主服务的 `build_jobs` 仍是唯一队列和恢复事实源；不能把 Dockerfile 默认端口或示例域名当作已生效的 `RUNTIME_EXECUTOR_URL`。
3. 所有用户共享一个执行服务，初始全局并发为一。每次任务在独立临时目录中物化源码，完成固定构建、单元测试和确定性校验后立即清理。
4. 执行服务先通过 `/health` 和私有调用验收，再把主服务的 `RUNTIME_EXECUTOR_URL` 指向私有地址。生产环境没有进程内回落；执行服务不可用时，构建明确失败或保持排队。

完整的接口、适配器、安全、恢复和验收边界见[共享独立执行服务设计](../features/04-执行与验证环境/06-共享独立执行服务/02-技术总设计.md)。该方案只是服务级隔离，Railway 非特权容器不能被描述为每任务独立强沙箱。

## 6. 当前部署边界

- Railway 账户、Volume 和实际资源会产生平台用量；本仓库不承诺免费额度。
- Railway 项目、实际地址和部署状态只登记在本地；每次操作仍需刷新实际版本，这些事实不替代数据库、私网调用或功能验收。
- Dockerfile 已提供；本轮未重新构建镜像或读取 Railway Build Log，不沿用旧机器故障作为当前验证结果。
- 默认模型服务（Provider）是模拟服务（Mock）；配置 Ollama/DeepSeek 后可运行真实模型，但仍需用产品经理（Product Manager）、架构师（Architect）、工程师（Engineer）完整三角色链路和真实构建/测试/校验（Build/Test/Validation）验收产物质量。

## 7. 执行与编辑沙箱前置

上述主服务与共享执行服务的部署步骤不等于真实构建/测试或源码 WebIDE 已通过验收。目标部署的两个执行边界分开部署：

```text
浏览器 -- HTTPS/SSE/WSS --> 主服务（Railway 或 Linux VM）
                                  |
                                  +--> SQLite + 持久化卷
                                  |
                                  +--> Railway 共享执行服务
                                  |    固定构建 / 测试 / 校验器
                                  |
                                  `--> Linux 编辑沙箱宿主机
                                       受限 Vim / 伪终端（PTY）
```

共享执行服务部署在 Railway 同一项目和环境，只允许已登记受限适配器；它不替代交互式编辑沙箱。Linux 编辑沙箱宿主机必须支持无根容器（rootless container）、Linux 命名空间（namespace）和控制组（cgroup）。编辑沙箱（Editor Sandbox）使用非 root 用户、只读根文件系统、禁网、无平台密钥（Secret）、删除 Linux capabilities、seccomp、`no-new-privileges` 和 CPU/内存/磁盘/PID/时限上限；只挂载当前编辑会话（EditorSession）的临时工作树（worktree），且不包含 `.git`。

仅使用 Vim 受限模式（restricted mode）、目录前缀检查或 `chroot` 不能作为多用户隔离边界。部署环境无法提供上述机制时，xterm.js 入口必须关闭。正式落地可以选择：

1. Railway 承载主服务和共享执行服务，独立 Linux 虚拟机（VM）承载编辑沙箱宿主机；
2. 若后续迁移到自管 Linux VM，也必须保留主服务、共享执行服务和编辑沙箱的进程、凭证、挂载和网络边界，不能因部署在同一台机器便合并职责。
