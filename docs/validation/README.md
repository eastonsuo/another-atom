# 开发侧自测方案与执行记录规范

本目录回答“指定 Feature 的明确实现，在明确非生产环境和不可变版本上是否满足本次开发侧验收合同”。部署健康、代码测试和环境功能验证是不同证据，不得相互替代。

## 1. 唯一记录

一个 Feature 只维护一份自测方案与执行记录，推荐命名：

```text
YYYY-MM-DD-中文主题-自测记录.md
```

同一文件持续保存方案、部署批次、用例结果和开发侧结论。不要另建功能验收方案、部署验收记录或 Validation Handoff。

## 2. 来源与范围

开发侧必测范围是以下三者的交集：

```text
用户确认的本次交付范围
∩ 已确认 Code Spec 中适用的验收合同
∩ 本次实现及其直接影响边界
```

记录必须链接唯一 Code Spec、适用技术总设计、代码提交和实际目标环境。超出开发责任边界的内容只记录为联调依赖或测试建议，不能混入必测通过结论。

## 3. 记录结构

每份记录按实际内容保留：

1. Feature、Code Spec、交付范围与非目标；
2. 本地验证结果及其命令、时间和代码基线；
3. 环境批次：环境级别、环境标识、主服务与 executor 实际不可变版本、入口和部署读回；
4. 用例：场景、Fixture、操作、预期、失败判定、实际结果、执行主体、时间和证据；
5. 阻塞、未覆盖合同和责任入口；
6. 开发侧结论。

版本、配置、数据或依赖变化可能影响结果时建立新环境批次，不覆盖旧事实。

## 4. 用例状态

- `PASS`：真实执行满足预期，且有可复核证据；
- `FAIL`：合同被真实执行，但实现结果违反预期；
- `BLOCKED`：环境、身份、凭证、工具、Fixture、依赖或版本问题使合同没有被有效执行；
- `NOT_RUN`：场景已纳入方案，但尚未执行。

只有当前不可变版本上的全部必测用例均为 `PASS`，才能记录“开发侧自测门禁满足”。这不等于测试人员正式验收或生产发布许可。

## 5. 职责边界

- `implement-code-change`：业务代码、测试、静态检查、前端 lint/build 和可执行的本地真实边界集成；
- `deploy-for-validation`：制品、部署、Rollout、健康、入口、实际版本读回、环境恢复；
- `validate-in-non-production`：自测方案、验证侧 Preflight、Smoke、API、页面、E2E、结果和开发侧结论。

产品缺陷返回代码实施；部署或环境问题返回部署处理；权威合同无法唯一决定预期时返回设计和 Code Spec。失败与重测追加记录，不能覆盖旧结果。
