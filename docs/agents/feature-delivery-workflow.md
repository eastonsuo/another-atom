# Feature 交付工作流

本文规定 Another Atom 从功能设计到代码实施和非生产验证的项目级路由。它只负责选择当前阶段、检查门禁和连接既有 Skill，不替代各 Skill 的详细规则，也不允许 Agent 自动确认自己的产物。

## 1. 主流程

先从 [Feature 索引](../features/README.md)经能力域定位具体 Feature，读取对应入口登记的当前设计和相关共同基线。能力域只负责分类，交付、Spec 和自测仍落到明确 Feature 与实施范围，不在域级另建一套合同。正文现行位置与旧路径来源见[迁移映射](../features/文档归属与迁移映射.md)，旧路径不再作为活动来源。Feature 入口是导航和证据摘要，不替代设计，也不因登记目录而触发重新设计。

新增或改变产品行为、公共接口、数据语义、组件职责、跨组件合同、故障、兼容或迁移时，按以下顺序推进：

```text
产品与技术设计
  → 技术总设计已确认
  → Code Spec 派生
  → Code Spec 已确认
  → 代码实施与本地验证
  → 必要时部署非生产不可变版本
  → Smoke / API / 页面 / E2E 验证
  → 开发侧自测门禁满足
```

每个阶段完成后只报告当前结果、下一门禁和恢复条件。存在待确认产物、写入授权或环境授权时停止；“完整推进”“做完这个 Feature”等宽泛指令不等于用户已经确认尚未生成的设计、Spec 或 Plan，也不等于部署授权。

## 2. 阶段与入口

| 问题 | 入口 | 必要输入 | 阶段结果 |
| --- | --- | --- | --- |
| 产品应该怎样工作、技术如何保证 | `write-design-doc` | 已确认产品基线、相关代码、目标文件写入授权 | Feature 登记的专项设计或 `docs/design/**` 中的共同基线 |
| 如何把技术总设计变成实施合同 | `derive-code-spec` | 已确认且本轮核对稳定的技术总设计、Feature 和实施范围 | `docs/superpowers/specs/**` 中的候选或已确认 Code Spec |
| 是否需要持久任务账本 | `write-implementation-plan` | 已确认 Code Spec；用户明确要求或复杂任务确有需要 | `docs/superpowers/plans/**` 中唯一当前 Plan |
| 如何修改代码并证明本地正确 | `implement-code-change` | Feature 使用已确认 Code Spec；维护修改使用能够唯一确定的既有行为 | 代码、测试、本地验证和提交 |
| 如何准备或改变验证环境 | `deploy-for-validation` | 已登记环境、不可变版本、明确目标和写入授权 | 制品、部署及实际版本读回事实 |
| 已部署实现在环境中是否满足合同 | `validate-in-non-production` | 已确认 Code Spec、唯一自测记录、已登记非生产环境和不可变版本 | 实际用例结果、证据和开发侧结论 |

Skill 可以根据用户请求自动选择，但不会自动跨越阶段。用户也可以显式指定 `$write-design-doc`、`$derive-code-spec`、`$implement-code-change`、`$deploy-for-validation` 或 `$validate-in-non-production`。

## 3. 权威关系

```text
docs/design/** 共同基线 + Feature 登记的专项设计
  └─ 每项合同一个权威落点，以 Feature 入口登记的现行正文为准
       ↓ 受控派生
docs/superpowers/specs/**
  └─ 指定 Feature 和实施范围的唯一 Code Spec
       ↓ 可选拆解
docs/superpowers/plans/**
  └─ 复杂 Feature 的唯一当前任务账本
       ↓ 实施与验证
代码 + docs/features/<能力域>/<Feature>/10-自测方案与执行记录.md
```

- Code Spec 必须是技术总设计的受控子集，不能补充设计决定。
- Plan 只组织实施，不摘要或改写 Code Spec，也不构成部署授权。
- Issue 负责执行协作状态；Review 负责完备性检查；Bug 负责既有合同的实现缺陷。三者都不是设计或 Spec 的替代品。
- 一个 Feature 不得并存多个当前 Code Spec、多个当前 Plan 或多份自测执行记录。
- 专项产品与技术设计、Spec、自测记录持续维护；执行证据按版本追加。Review 和 Bug 保留原始发现及 dated Update，不随 Feature 整理重写历史。
- 已完成 Feature 复用现有设计和证据，不补历史 Spec、Plan、确认或测试记录。只有维护依据存在实质缺口时才补说明；基于代码补录的现状不自动成为已确认设计。下一次改变合同前，为明确范围核对设计并派生或更新 Spec。

## 4. 确认门禁

### 4.1 技术总设计

用于派生 Code Spec 的设计必须在元信息中明确记录：

- 当前状态为已确认；
- 确认主体和日期；
- 可定位的书面确认依据；
- 本次 Feature 的范围、非目标和验收合同没有未关闭的设计问题。

本流程启用前已经存在的 Design 不批量改写。首次作为某个新 Feature 的派生来源时，只核对并补充该 Feature 实际涉及的确认状态；状态不清时先返回设计阶段。

### 4.2 Code Spec

Code Spec 状态只有：

- `待书面审阅`：候选已经完整，但尚未确认；
- `已确认`：当前候选已由用户接受，并记录确认主体、日期和可定位依据；
- `需重新审阅`：技术总设计变化或高影响实施合同变化使旧确认失效。

只有 `已确认` 的 Code Spec 可以进入 Feature 实施。用户确认设计不等于确认 Code Spec。

同一 Feature 持续更新唯一当前 Spec，保持路径稳定，并记录来源设计版本、代码基线和本次实施范围。技术设计或实施合同发生实质变化时更新受影响条款、验收和下游引用，并进入`需重新审阅`；仅修正文案或链接、不改变合同的修改保留确认依据。每次开始实施仍须重新核对当前技术总设计，不能仅凭旧状态继续。

### 4.3 Implementation Plan

Plan 默认可选。只有用户明确要求，或任务跨仓、依赖复杂、需要多轮维护状态时才创建。Plan 候选需单独确认后才能成为可执行账本；Code Spec 的确认不自动确认 Plan。

### 4.4 部署与验证

代码实施授权不包含部署。部署必须明确目标环境、对象、不可变版本和允许动作；验证必须明确目标环境、版本、用例范围和访问授权。部署完成只证明环境事实，不等于功能验证通过。

## 5. Feature 与维护修改分流

符合下列任一条件时按 Feature 处理：新增或改变产品行为、公共接口、数据语义、组件职责、跨组件合同、故障、兼容、迁移、容量或成本承诺。没有已确认 Code Spec 时，不直接修改代码。

只有正确行为能够由现有设计、接口、测试、复现或历史行为唯一确定，且修复不改变上述合同时，才按 Bug／维护模式直接实施。实现过程中发现需要新的设计决定时，立即停止受影响修改并回到设计阶段。

## 6. 实施澄清

本个人项目登记 `docs/features/<能力域编号>-<能力域名>/<稳定编号>-<中文功能名>/11-实施澄清记录.md` 为当前 Feature 的持久澄清位置。用户已授权本轮目录调整，澄清位置随 Feature 更新；后续在已授权的 Feature 工作范围内按需创建，并由该 Feature 入口链接。已有依据不能唯一决定、会形成持久实施基线的语义冲突或工程取舍记录以下内容：

- 待决对象；
- 现有设计和代码依据；
- 候选差异及长期影响；
- 受影响阶段和任务；
- 建议处理与恢复条件。

记录待确认／已确认结论、实际确认依据和日期，以及结论回写位置。普通工程困难、机械修改、临时故障和一次性操作授权不进入记录，不为占位创建空文件。

完整讨论只放在该记录，不复制进 Design、Code Spec、Plan、Issue、提交信息或源码文件。已确认的语义变化先回写权威设计，再更新并确认 Spec；不改变设计的持久工程取舍落实到适用 Plan、代码或项目配置。澄清记录不替代这些门禁，也不构成部署授权。

## 7. 完成口径

- 代码实施完成：适用 Code Spec 已实现，必要且可执行的本地检查有真实结果；未执行的环境验证明确保留。
- 已部署：目标环境实际运行版本已经读回；异步部署仅受理时不得写成已部署。
- 开发侧自测完成：当前不可变版本的全部必测用例均有真实证据并通过。
- Feature 完成交付：除本地实现外，还满足设计要求的部署环境验证和用户可见验收；不能用局部完成概括整体完成。
