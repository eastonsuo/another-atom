# 验证环境登记规范

本文只保存可提交的环境登记规范、字段模板、版本读回方法和访问边界。真实环境信息存放在本机的 `docs/agents/validation-environments.local.md`，不进入 Git。CLI 操作步骤见[运行与部署](../operations/01-运行与部署.md#50-使用已有项目cli-入口)。

## 1. 分层保存与读取约定

- **仓库内**：本文、通用部署说明、带占位符的命令，以及 `railway.toml`、Dockerfile 等可复用配置。
- **仅本地**：`docs/agents/validation-environments.local.md` 保存用途与实际项目的映射、Project／Environment／Service ID、实际公网与私网入口、Volume 信息、来源分支和带日期的部署快照。该文件由 `.gitignore` 和 `.dockerignore` 排除，不强制暂存，不作为构建输入。
- **凭证**：Token、Cookie、密码、模型密钥和共享令牌值不进入上述任一文档；由 Railway 或本机官方登录机制管理，只登记非敏感的来源和引用关系。

Agent 先读取本文，再按本次任务范围读取本地登记，并通过只读查询核对实际目标。只有通用模板不能证明环境已登记；本地文件不存在、字段不全或身份不匹配时，停止受影响的写入或验证，报告具体缺口，不从示例、环境显示名、上次 CLI 默认关联或其他项目猜测目标。用户已授权且能唯一定位目标时，可以继续限定范围的只读核对。

本地文件不会随 clone、pull 或构建自动迁移。换机器时需要单独迁移或重新核对登记；未取得本地记录，不代表实际环境不存在。路径和用途登记不构成部署、测试或凭证读取授权。

## 2. 验证环境类型

| 类型 | 可证明范围 | 版本与执行入口 | 不能替代的证据 |
| --- | --- | --- | --- |
| 本机验证 | Python 单元／集成测试、静态检查、Studio lint/build，以及按任务实际装配的本地真实边界 | Git commit；工作区非干净时同时记录 diff 范围。仓库根目录可执行 `uv run pytest`、`uv run ruff check another_atom tests`；`studio/` 可执行 `npm run lint`、`npm run build` | Railway 网络、Volume、私网 executor、部署后重启及公网行为 |
| 已登记 Railway 目标 | 明确环境与不可变版本上的部署状态；获授权后执行适用环境用例 | 从本地登记取得 Project、Environment 和 Service ID，分别读回主服务与执行服务版本 | 控制面存在、`SUCCESS` 或 `READY` 不等于功能用例 `PASS` |

本地命令只在合同和改动范围适用时执行，不要求每次机械运行全部检查。环境级别按实际用途、流量及数据关系判断，不能由 `production`、`test` 等名称单独决定；生产或共享生产数据目标不进入非生产验证。

## 3. 本地登记模板

下面只定义字段，不是可执行目标。核对后把真实值填入本地登记；按每个实际环境分别记录，不创建占位环境或空验证批次。

```text
用途标识：<本机可区分的目标别名>
用途与环境级别：<用户确认来源、日期、实际用途及数据关系>
核对时间：<时间与时区>
项目（Project）：<实际名称、ID>
环境（Environment）：<实际名称、ID；必须属于上述 Project>
代码来源：<仓库、绑定分支；分支名不是不可变版本>
推送影响：<绑定同一分支的目标范围、已核对的自动部署设置与未确认项>
主服务：<名称、Service ID、配置文件、公网入口、目标端口>
执行服务：<名称、Service ID、配置文件、真实私网 DNS、已核对的监听端口>
持久化：<所属服务、Volume ID、挂载路径、状态、适用数据库与依赖>
主服务版本：<活动 Deployment ID、Git commit、镜像摘要、实例状态、读回时间>
执行服务版本：<活动 Deployment ID、Git commit、镜像摘要、实例状态、读回时间>
验证身份：<安全来源与引用，不写凭证明文>
操作边界：<本次允许动作、授权来源、失败停止条件、恢复锚点与清理责任>
未确认项：<仍缺少的身份、装配、依赖或功能证据>
```

同名环境或服务可能属于不同项目；始终按同一目标配对 Project、Environment 和 Service ID。控制面目标、实际入口、挂载卷与版本读回必须相互匹配。不同资源 ID 不自动证明外部依赖、数据库连接或模型账户已隔离。

## 4. 版本读回与核对

每次操作使用显式目标的 `railway status --json`，从匹配 `environmentId`、`serviceId` 的 `activeDeployments` 读取 `id`、`status`、实例状态、`meta.commitHash`、`meta.imageDigest` 和 `meta.configFile`。`latestDeployment` 可能仍在构建或已经失败，不能单独证明当前运行版本。用 `railway deployment list` 按服务补查历史，用 `railway private-network status` 读回执行服务 DNS；完整命令见[CLI 入口](../operations/01-运行与部署.md#50-使用已有项目cli-入口)。

主服务与执行服务分别读回版本，不用一个服务的结果推定另一个服务，不把旧快照当作永久有效的当前状态。实际端口、主服务 `RUNTIME_EXECUTOR_URL`、共享令牌引用、依赖就绪和测试数据影响按当次请求核对；默认不读取令牌明文，也不把 Dockerfile 的默认端口当作实际装配证据。

## 5. 访问与动作边界

- 优先使用项目已有 CLI 或已登记入口，复用官方机制维护的登录身份。登录失效时走官方登录，不导出认证缓存，不因缺少 MCP 自动安装或更改全局配置；本机工具与认证检查结果仅记入本地登记。
- 只读查询限定本次目标；日志查询还需限定服务、版本和时间窗口，不为状态检查读取完整环境变量或配置。
- 部署、重部署、重启、配置修改、环境创建、测试数据写入、模型调用和删除按当前任务分别取得适用授权。用途为个人开发，不代表已有项目、数据库或文件可任意清理。
- 推送前核对绑定分支可能影响的全部项目与服务。只授权一个测试目标，不代表已授权影响其他目标；未确认自动部署和 Watch Paths 设置前，不假定纯文档提交会被忽略。
- 环境用途、流量或数据关系改变后，重新核对环境级别和授权边界；应用变量、平台显示名和实际用途是不同事实。

## 6. 保存验证证据

通用规范不保存资源清单、当前部署状态或完整查询输出。本地登记保存真实环境映射和带日期的必要读回；实际 Feature 的方案、用例状态与结论仍只维护于该 Feature 的唯一[自测方案与执行记录](../validation/README.md)。

提交的 Feature 记录使用用途别名和批次编号关联本地环境证据，保留代码提交、执行时间、用例结果与脱敏结论，不复制资源 ID、实际入口、部署快照或完整日志。需要保存原始环境读回时，在本地登记中按 Feature 与批次追加；这不是第二份用例状态。历史证据不得因当前环境变化被重写。

没有对应 Feature 的只读调查在当次回复交付，必要的环境映射保留在本地登记；未执行功能用例时，不补建空自测批次，也不把控制面 `SUCCESS` 或 `READY` 写成 `PASS`。
