# Another Atom 设计文档规范与索引

[toc]

## 背景

随着 V1、V2、整体原则和参考资料逐步增加，仅靠目录和文件名已经不足以区分正式 Contract、计划能力与历史检查。设计文档需要统一职责、版本归属、命名和首屏信息，避免同一结论分散在 Design、Review 和 README 中。

## 摘要

- **文档职责**
  - `docs/design/` 保存跨 Feature 的共同基线，`docs/features/` 组织功能专项设计与交付入口；Review 保存完备性检查，Bug 保存实现缺陷证据。
- **内容分类**
  - 产品需求与交互合并维护，技术设计区分 Agent 与工程问题。
- **目录与版本**
  - 共同基线保留 V1、V2、整体分类；Feature 使用稳定目录，版本和交付状态写入元信息。现有正文尚未搬迁，当前路径以 Feature 登记为准。
- **首屏要求**
  - 每篇正式设计文档在元信息后先写“背景”和“摘要”，摘要使用缩进列表提炼要点。

## 1. 文档职责

设计回答“产品应该怎样工作、技术如何保证它成立”。`docs/design/` 保存整体产品、版本范围、角色职责、系统架构、跨功能流程和部署共同基线；`docs/features/<稳定编号>-<中文功能名>/` 保存功能专项设计。每项合同只有一个正式落点，其他文档引用它。检查和阶段证据进入 [`docs/review/`](../review/README.md)，实现缺陷进入 [`docs/bug/`](../bug/README.md)。

迁移入口见 [Feature 索引](../features/README.md)和[文档归属与迁移映射](../features/文档归属与迁移映射.md)。第一步只登记归属，本文下方现有链接继续有效；未迁移设计仍在原文件维护，不在目标目录创建副本。仅在后续迁移实际完成时更新映射、入口和反向链接。

设计文档只分为两类：**产品设计**和**技术设计**。

### 1.1 产品设计

产品设计回答“做什么、为谁做、为什么这样做、用户最终看到什么”。内容可以包括：

- 产品目标、目标用户、版本范围和明确不做；
- 用户路径、信息结构、页面与交互；
- 用户可感知的状态、失败出口和能力边界；
- 功能验收标准、关键产品取舍及适用边界。

产品需求和产品层设计写在同一份文档中，不再维护相互重复的 PRD 与交互设计。产品设计可以定义需要哪些 Contract，但不展开 API、表结构、调度算法、部署命令或 Sandbox 实现。

### 1.2 技术设计

技术设计回答“如何实现并可靠地满足产品设计”。共同基线与未迁移文档仍使用版本内的`技术设计/`目录和文件名 Tag；Feature 专项设计通过稳定文件名和元信息说明职责：

- `Agent`：角色职责、输入输出 Contract、Context、Memory、编排、Handoff、Tool、Human-in-the-loop，以及 Agent 与确定性 Runtime 的控制边界；
- `工程`：系统架构、API、数据与持久化、状态推进、并发、恢复、安全、Sandbox、测试和部署。

同一问题只保留一个主要事实源。涉及另一个领域时通过链接引用，不在多份文档中复制完整定义。Tag 按文档主要回答的问题选择，不因作者或临时工作阶段变化。

### 1.3 首屏结构

每篇 Design 文档在标题、`[toc]` 和元信息之后，正文之前固定写：

1. **背景**：用一至两段说明本文在做什么、为什么需要这篇文档，以及它解决的具体问题；不在背景中提前展开完整方案。
2. **摘要**：使用缩进列表展示文章要点，不写成连续长段落。一级列表按正文中相互独立的同层问题组织，二级列表写对应结论；只提炼正文已有内容，不新增正文无法支撑的判断。要点数量由文章实际内容决定，不设固定数量，不为保持格式对称而强行拆成三条或凑维度。

推荐格式：

```markdown
## 背景

本文用于……，解决……。

## 摘要

- **核心结论**
  - ……
- **范围边界**
  - ……
```

## 2. 版本范围

- `V1`：当前实现和验收基线；V1 完成前不把 V2 能力写成当前事实。
- `V2`：V1 验收后的计划版本；所有能力默认视为未实现。
- `整体`：跨版本长期有效的产品原则和外部参考资料，不作为版本归属不清时的临时目录。

共同基线的版本说明和入口维护在本文，具体功能入口维护在 [Feature 索引](../features/README.md)。Feature 适用版本写入元信息，不因迭代变更目录编号。

## 3. 目录与编号

```text
docs/design/
├── README.md
├── V1/
│   ├── 产品设计/
│   └── 技术设计/
│       └── NN-[Agent|工程]-中文主题.md
├── V2/
│   ├── 产品设计/
│   └── 技术设计/
│       └── NN-[Agent|工程]-中文主题.md
└── 整体/
    └── NN-[产品|参考]-中文主题.md
```

版本内产品设计文档使用 `NN-中文主题.md`，例如 `01-核心产品需求与交互.md`；技术设计文档使用 `NN-[Agent|工程]-中文主题.md`，例如 `03-[工程]-系统架构.md`；`整体/`使用 `NN-[产品|参考]-中文主题.md`。序号只表示同一目录内的建议阅读顺序，不表示优先级或实施状态；已有链接建立后，不因临时插入文档随意重排。

已有 `[TODO]` / `[DONE]` 文件名在本次入口登记中保留，其含义仍是交付范围是否完成。新建或后续迁移的 Feature 设计使用稳定文件名，设计确认、代码实现和环境验证分别记录在元信息中，不再通过改名推进状态。Feature 内具体目标文件见迁移映射；产品与技术已合写且边界清晰的文档可以继续合写，不强制拆成两个空缺文件。

已完成 Feature 优先关联既有材料，不批量补写设计、Spec、Plan 或自测历史。只有存在实质维护缺口时才补必要说明；基于代码恢复的说明必须标明实际补录日期和证据，不能反推原设计意图或倒填确认。

Review 文件使用全局稳定编号和类型 Tag：`NN-[产品|Agent|工程|综合]-YYYY-MM-DD-中文短主题.md`；从待办移入归档时文件名不变。

Bug 文件使用 Bug 目录内的独立稳定编号：`NN-[产品|Agent|工程|综合]-YYYY-MM-DD-中文短主题.md`；从待办移入归档时文件名不变。Bug 修复默认不修改 Design；只有预期行为或 Contract 需要改变时才先修订 Design。

## 5. 与 Review、Bug 的关系

```text
design 定义预期
  -> 实现
  -> review 检查功能是否完备
  -> bug 记录实现对既有预期的违反
  -> 需要长期生效的结论回写 design
```

Design 可以持续修订；dated Review 和 Bug 保留历史原貌，通过追加 Update 记录后续结论与验收。单纯修复代码实现错误不要求改 Design；只有修复需要改变既有预期时，才先把新结论写入 Design。讨论稿、问答、测试数量、当前完成度和一次性检查结论不作为长期 Design 单独维护。
