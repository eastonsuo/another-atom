## 背景

Another Atom 要交付的是用户能持续修改和掌控的项目，不是一次模型回答。多角色、编辑、校验和发布都围绕同一个 Project 工作，版本演进不能割裂项目历史或改变用户原始目标。

## 摘要

- **项目连续性**：需求、设计、源码、验证结果和版本属于同一个长期存在的 Project。
- **目标与运行能力分开**：接受任意软件产品目标，不代表平台已经能执行任意代码；预览只是有匹配运行能力时的附加结果。
- **用户控制**：Agent 提出方案，平台执行确定性约束；产品确认、线上变更和高风险操作不能由 Agent 代替用户决定。

## 产品的取向

默认由一个 Lead 面向用户。专业角色分别解决产品、架构和实现问题，并交付可检查的产物；角色数量、同时发言或表面自治不是产品目标。具体职责由 [Feature 10](../features/01-角色职责与能力/10-角色职责与交付物/README.md)维护。

自然语言、文件编辑、可视化编辑共同作用于同一个项目。修改应从明确的需求和版本基线继续；Remix 用于独立分叉，不应成为每次失败后丢弃上下文的替代品。详细行为分别归对话修改、文本编辑和版本发布 Feature。

原生应用、CLI、桌面端或服务端需求不能为了适配网页预览被改成 Web。能够保存源码与版本、能够在线运行、能够发布是不同能力；缺少运行适配器时应明确交付状态，关键能力不足也不能静默模拟。精确结果语义由 [Feature 07](../features/05-产物与交付部署/07-通用源码与运行校验/README.md)维护。

先证明从需求到持续修改和交付的真实闭环，再评估后端、连接器、增长和协作广度。能力中心可以解释未提供的能力，不能制造已经接通服务的假象。

## 与参考产品的关系

Atoms 是公开产品材料的参考，不是内部架构、私有 Prompt 或功能完成度的证据。保留其“需求—生成—检查与修改—版本—发布”这一参考主线，但采用 Another Atom 自己的交互、合同和工程实现。原始分析保留在[参考资料](../references/Atoms参考产品分析.md)，不作为当前产品需求的第二份来源。

## 判断标准与功能演进

判断产品是否成立，重点看用户目标是否被保留、修改是否成功、过程是否可理解、源码与版本是否可追溯，以及用户能否持续控制交付结果。对于仅源码就绪的项目，不以缺少浏览器预览否定源码交付，也不把它说成已经可以运行。

固定执行、任务图、局部并行、受控工具与证据驱动返工分别由对应 Feature 持续维护，不再划分产品大版本。具体推进取决于用户选择的范围、依赖与确认状态，见[功能范围与整体验收](./04-功能范围与整体验收.md)。
