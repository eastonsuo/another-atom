# 端到端流程

[toc]

- 适用范围：固定串行创建与持续修改；任务图协作由 Feature 16 单独维护
- 更新日期：2026-09-29；性质：流程概览，不定义第二套状态或接口合同

## 背景

Feature 分别维护自己的规则，但用户经历的是一条连续流程。本文说明各 Feature 怎样接续；按钮、状态、异常恢复和验收细则仍回到负责它的 Feature。

## 摘要

- **首次创建**：表达目标 → 澄清并生成产品规格 → 用户确认 → 架构 → 源码与测试 → 适用校验 → 版本与交付。
- **持续修改**：基于已有项目确认修改任务，按影响选择合法固定入口，复用仍有效的上游依据。
- **失败与等待**：保留真实状态、已有版本和失败证据；等待输入、执行失败、用户主动停止不能混用恢复语义。

## 首次创建

用户登录工作台，以文字及可选参考图片向 Lead 表达目标。Lead 直接回答、提出澄清问题或调用团队；直接回答不制造虚假的构建和版本。

进入团队后，PM 形成完整产品规格，用户确认当前内容后再进入 Architect 和 Engineer。工程师交付真实源码与测试，平台根据运行能力执行适用校验并形成结果；模型自报成功不能替代验证证据。

## 已有项目修改

[Feature 04](../features/02-任务规划与执行编排/04-对话式代码修改/README.md)负责修改任务、源码上下文和固定入口选择。用户已确认三个固定入口的产品方向，但该入口选择尚待技术确认与实现；不是当前已经可用的任意步骤续跑。

复用上游依据不等于跳过批准、版本基线或适用校验。执行中若必须改变被跳过的上游设计，停止并重新确认任务，不自动跨角色回退。

## 等待、失败与上线

等待人工补充或批准由 Feature 03 恢复原任务；失败后的 Retry 由 Feature 11 在同一项目创建新执行并保留失败记录。用户主动停止后支持按阶段继续同一任务：复用有效的已完成阶段，重跑中断阶段；[PQ-02](../features/02-任务规划与执行编排/11-固定串行执行/产品澄清.md#pq-02) 已确认该产品目标，详细规则归 Feature 11，技术设计与实现尚待完成。

版本形成不等于发布。手工源码保存与 AI 修改统一先形成新版本供预览检查，再由用户显式发布／更新，不自动改变线上内容。确认依据与详细边界只在 Feature 12 的 [PQ-05](../features/05-产物与交付部署/12-版本预览与发布/产品澄清.md#pq-05) 及关联规则维护。
