- 整理日期：2026-09-28；依据既有执行服务设计提取，不新增执行能力
- 设计来源：[共享独立执行服务技术设计](./02-技术总设计.md)

## 背景

用户需要知道 AI 生成的代码是否真的构建、测试和通过校验。模型声明“已通过”不能作为证据；同时，执行生成代码不能直接取得主服务的业务密钥和持久化数据。本功能把受限执行放到独立服务中，并把真实结果交还给主服务。

## 摘要

- **交付结果**
  - 向用户提供真实构建、测试和校验状态及报告；失败时保留证据，不创建伪成功版本。
- **运行边界**
  - V1 所有用户共用一个受限执行服务，属于服务级隔离，不承诺每用户或每任务独立强沙箱。
- **控制归属**
  - 用户权限、审批、排队、预算和版本仍由主服务负责；执行服务只执行受支持的固定计划。

## 1. 用户可见流程

用户确认产品方案后，固定角色链路生成候选源码和测试；系统按“排队 → 准备源码 → 构建 → 测试 → 校验”推进。只有证据满足当前项目类型的运行要求，候选才能成为可运行版本。

界面应展示真实阶段、成功或失败原因、可查看的报告，以及当前版本是否变化。排队不显示没有依据的预计完成时间。不同用户共享执行容量，排队规则需要避免某个用户长期占满执行机会。

没有匹配运行能力的项目走 [Feature 07 的源码交付路径](../07-通用源码与运行校验/01-产品说明.md)，不能悄悄改成 Web 项目，也不能把未执行的代码标为已经通过测试。

## 2. 失败、取消与恢复

- 源码或测试问题：保留失败阶段与报告，允许固定预算内的工程师修正；不能让模型改写执行结论。具体候选修正合同归 [Feature 04](../04-对话式代码修改/README.md)。
- 执行服务不可用、通信中断或平台故障：明确显示基础设施失败，不将其伪装为代码错误反复改源码。
- 超时或取消：停止后续执行及版本写入；正在运行的任务必须确认执行已终止，不能只改界面状态。排队取消与运行中取消是不同情形。
- 服务重启或结果丢失：识别失联执行并保留可追溯状态，恢复不得重复创建版本或把不完整报告当成成功。
- 执行结束：成功、失败、超时、取消均需清理临时执行目录；失败不改变最后可用版本和线上版本。

这些是产品目标，不表示统一 Stop 按钮和跨服务取消已经完成验收。

## 3. 明确不做

V1 不提供任意 Shell、动态安装依赖、不受限网络或任意原生后端工具链执行；不为每个用户或每个任务建立独立强沙箱。不把扩大执行能力作为文档整理的一部分。

独立服务不得挂载主服务持久化卷或持有业务密钥。其真实部署隔离条件必须在目标环境核验，仅有代码目录拆分不能证明成立。

## 4. 验收重点

1. 用户能区分排队、实际执行、执行失败与源码错误；报告绑定本次候选，不接受模型自报成功。
2. 固定 Build/Test/Validate 真正运行，缺失或不匹配的结果不能推进可运行版本。
3. 多用户竞争、服务中断、取消和超时均有明确终态；不重复执行或写版本。
4. 执行服务的网络、密钥、持久化卷和临时目录边界在 Railway 环境得到验证。
