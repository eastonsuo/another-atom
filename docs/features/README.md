## 文档位置与维护方式

Feature 目录命名为 `<稳定编号>-<中文功能名>`，编号不表示优先级，后续迭代沿用原目录。适用版本、确认依据和交付状态写入元信息。

| 材料 | 位置与规则 |
| --- | --- |
| 功能入口 | 每个 Feature 的 `README.md`，链接范围内的当前设计、Spec、可选 Plan 和证据 |
| 产品与技术设计 | 位于 Feature 内；已有材料在迁移前沿用当前正文。一个合同只保留一处定义，可按实际需要合写或保留专项设计 |
| 正式 Code Spec | `docs/superpowers/specs/`，与 Feature 入口双向关联，唯一当前文件持续更新 |
| 可选 Implementation Plan | `docs/superpowers/plans/`，需要持久任务账本时才创建，不为目录齐全补建 |
| 自测方案与执行记录 | Feature 内 `10-自测方案与执行记录.md`，方案持续维护，执行结果按实际版本追加批次 |
| 实施澄清 | Feature 内 `11-实施澄清记录.md`，需要确认持久工程取舍时按需创建，结论回写正式依据 |
| 产品澄清与技术讨论 | 存在实际问题时按需保存；已确认合同回写产品／技术设计，讨论记录不构成第二份设计 |
| 资源 | 新增专属资源按需进入 Feature 内 `assets/`；已有资源保留原路径至实际迁移 |
| Review 与 Bug | 保留原有证据目录和编号，Feature 入口引用；不复制、不因入口建立改变归档状态 |

设计与 Spec 的确认、实施模式和阶段路由以[交付工作流](../agents/feature-delivery-workflow.md)为准，Spec／Plan 的维护方式见[实施合同规范](../superpowers/README.md)，自测内容见[公共自测规范](../validation/README.md)。路径登记不创建对应文件，也不增加部署授权。

## 已完成功能如何处理

已有设计直接关联；材料分散时确定各自职责；只有缺少后续维护所必需的依据时才补必要说明。不批量补历史设计、Code Spec、Plan、确认或测试结果。由代码恢复的说明标明实际补录日期和证据，不能反推历史决策。

本批入口的状态摘要来自所链接原文，不是新的代码审计或部署验收。后续更新入口时，分别说明设计确认、代码实现、部署和环境验证，并链接证据；GitHub Issue 继续负责执行待办，不在入口复刻任务账本。文档内部或相互之间存在矛盾时标为待核实，先保留来源。

## 后续迁移边界

第二步按迁移映射逐项移动正文、修正有证据的状态偏差和更新所有反向链接。迁移完成前继续修改登记的当前来源；不得同时在旧目录和目标目录维护两份设计。跨 Feature 基线与各专项有不同职责，登记归属不授权改变合同。

本步没有派生 Spec、修改业务代码或执行环境验收。当前 Railway 非生产目标仍以[验证环境登记](../agents/validation-environments.md)为准；本地检查不能替代尚未完成的环境验证。
