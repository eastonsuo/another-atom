## 文档位置与维护方式

目录格式为 `docs/features/<能力域编号>-<能力域名>/<Feature稳定编号>-<中文功能名>/`。能力域编号只用于分类；Feature 编号在全目录唯一，01–09 沿用原标识，新增项从 10 继续，不在各域重新编号，也不代表优先级。后续迭代沿用稳定目录，适用版本、确认依据与交付状态记录在正文中。

| 材料 | 位置与规则 |
| --- | --- |
| 能力域入口 | 大目录内 `README.md`，说明归属边界并链接本域 Feature，不维护第二份需求或实施合同 |
| 功能入口 | Feature 内 `README.md`，链接当前设计、Spec、可选 Plan 与历史证据 |
| 产品说明 | Feature 内 `01-产品说明.md`，维护目标、范围、用户行为、验收与当前差距 |
| 技术设计 | Feature 内按实际需要维护总设计或专项设计，不补造缺失的历史设计 |
| 正式 Code Spec | `docs/superpowers/specs/`，唯一当前文件持续更新，与 Feature 入口双向关联 |
| 可选 Implementation Plan | `docs/superpowers/plans/`，确需持续任务账本时创建 |
| 自测方案与执行记录 | Feature 内 `10-自测方案与执行记录.md`，按实际不可变版本追加验证批次 |
| 实施澄清 | Feature 内 `11-实施澄清记录.md`，记录需确认的持久工程取舍，结论回写正式依据 |
| 产品澄清、技术讨论及资源 | 有实际内容时按需建立；讨论不替代正式设计，资源不为目录对称机械搬动 |
| Review 与 Bug | 保留原证据目录和编号；Feature 只引用，不复制或机械归档 |

设计与 Spec 的确认及阶段路由见[交付工作流](../agents/feature-delivery-workflow.md)，实施合同见[Spec/Plan 规范](../superpowers/README.md)，自测见[公共自测规范](../validation/README.md)。本次文档整理不构成任何阶段确认或部署授权。

## 产品说明如何持续更新

每个 Feature 都维护轻量产品说明，包括已经完成的 Feature。优先复用已有产品材料，代码只能证明当前行为，不能反推未确认需求。

整理中发现已有依据但未开发的能力，写入同一产品说明，并区分：

- 已有实现：写明覆盖的子路径与代码依据，不等同于完整验证。
- 尚未实现或与设计不一致：保留目标、缺口与来源，不把目标写成当前功能。
- 待验证：代码存在，但仍缺本地、页面或实际环境证据。
- 范围外／后续方案：已有明确边界，不自动排为当前开发待办；没有依据的需求只记为待确认。

设计确认、代码实现、提交推送、部署和验证是不同事实。产品说明的状态核对是轻量盘点，不能代替完整代码审计或交付验收。GitHub Issue 继续负责执行队列，不在文档中复制日常任务账本。

已完成的功能不补造历史技术设计、Code Spec、Plan、确认或测试结果；本轮补录统一标明实际日期与依据。后续更新产品与技术合同后，按影响重新核对持续维护的 Code Spec。
