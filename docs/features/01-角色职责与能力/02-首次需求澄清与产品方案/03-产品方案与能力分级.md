## 6.2 产品规格（ProductSpec）与项目创建

`docs/product-spec.md` 是产品经理（Product Manager）交付的完整产品文档，也是用户批准和下游交接的产品事实源。产品蓝图（Blueprint）保留为能力路由和结构化索引，不能取代产品规格（ProductSpec）成为架构师（Architect）的唯一输入：

```text
 Prompt + Attachments
          |
          v
 +------------------------+
 | ProductSpec            |
 | - Product goal         |
 | - Core flows           |
 | - Scope and boundaries |
 | - Failure feedback     |
 | - Acceptance criteria  |
 +-----------+------------+
             |
       inspect / edit / approve
             |
             v
          Build task
```

- 提交提示词（Prompt）后先创建草稿（Draft）项目，产品经理（Product Manager）生成产品摘要、完整 `docs/product-spec.md` 和同源产品蓝图（Blueprint）索引，不直接播放构建进度。
- 产品规格（ProductSpec）包含产品目标、用户场景、核心流程、功能与页面、输入输出、状态与失败反馈、范围与不做事项、能力边界和验收条件。
- 用户可查看摘要、打开完整 Markdown，并确认、要求修改或继续对话。
- `supported` 和 `adapted` 产品规格（ProductSpec）都必须绑定当前内容指纹由用户确认；未确认、文档已修改或能力结论为 `unsupported` 时不进入架构师阶段。
- 提示词（Prompt）、附件元信息、产品规格（ProductSpec）、产品蓝图（Blueprint）索引和确认结果必须随项目持久化。
- 本功能接受任意软件产品需求。产品经理（Product Manager）必须保留原始项目类型和目标平台，并根据当前是否存在对应源码、构建和运行适配器输出 `support_level`：`supported`、`adapted` 或 `unsupported`。
- `supported` 和 `adapted` 都通过产品规格（ProductSpec）向用户展示完整方案并等待确认；`adapted` 还必须列出被替换、忽略或映射的需求。
- `unsupported` 不为原请求创建构建任务（Build Job）。产品经理必须保留原始产品目标和项目类型，说明当前缺少的运行时适配器（Runtime Adapter）或工程能力；不得自动生成网页（Web）替代品。用户可以继续补充需求或要求产品经理重新整理，只有形成能力边界明确且经用户确认的方案后才能推进；后续是否构建或只形成源码版本，遵循 Feature 07 的运行绑定和 source_ready 规则。
- Product Manager 还必须输出 `support_reasons[]`、`mapped_requirements[]`、`omitted_requirements[]` 和 `rewrite_suggestion`，使三态判定可以解释和复核。
- 图片附件的格式、上传、移除和 Provider 边界统一见 [Feature 08](../../03-用户交互与协作/08-图片输入与视觉上下文/01-产品说明.md) 及其技术设计：图片会发送给配置的视觉 Provider；不得继续承诺“不上传到第三方服务”或“仅本地处理”。其他附件类型不借此扩展支持范围。
- Projects 的查看、重命名和删除统一由 [Feature 14](../../03-用户交互与协作/14-项目工作台与能力展示/01-产品说明.md) 维护。

<a id="p-supportlevel-判定规则与示例"></a>

## support_level 判定规则与示例

判定先看**主要用户目标**，不能只按关键词匹配：

| 判定 | 边界规则 | 典型输入 | 系统行为 |
| --- | --- | --- | --- |
| `supported` | 主要目标可以由当前项目类型对应的 Source/Build/Runtime Adapter 完成 | 当前已实现示例：“创建网页扫雷游戏”“制作 Web 看板” | 展示完整 ProductSpec 并等待用户确认；网页项目完成后提供 Preview |
| `adapted` | 项目类型和主要目标保留，但部分次要能力需要删减或替代 | “创建 Web CRM，但真实企业登录和云端客户数据暂不可用” | 保留 CRM 与 Web 目标；明确删减项并等待确认 |
| `unsupported` | 用户要求的主要结果依赖当前缺少的关键能力，且仅交付源码不能满足已确认范围 | “必须在平台在线运行原生 iOS 相机应用”，而当前没有 iOS Runtime Adapter | 停止原请求并说明能力缺口；不得改成 Web 相机或商品目录 |

一致性约束：

- `adapted` 不能虚构真实后端、认证、交易、外部网络或动态依赖已经可用。
- 如果被省略能力是用户主要目标，必须判为 `unsupported`，不能为了继续构建而降级成 `adapted`。
- 平台使用固定 Capability Policy 校验 Blueprint；同一输入、同一 Policy 版本必须得到相同的允许/拒绝边界。
- UI 必须同时展示原需求、映射结果和舍弃项。`supported` 和 `adapted` 用户确认的都是当前 ProductSpec 内容指纹；`unsupported` 只能继续对话或让 PM 重新整理，不是对原能力范围的放行。

<a id="p-124-golden-path-不定义产品类型"></a>

## 12.4 Golden Path 不定义产品类型

当前 Golden Path 使用 Web 项目，是因为浏览器 Preview、Validator 和 Public Route 已经形成可验收链路，不代表产品只接受 Web 需求。界面和文档必须分别说明“用户要求的项目类型”与“当前可用的 Runtime Adapter”：非 Web 项目不得被改写成 Web；没有对应运行适配器时应显示缺口；经确认交付源码的方案可按 Feature 07 形成 source_ready，不能把该状态当作已经运行，不能包装成已经支持任意构建、依赖、后端或 Shell。

<a id="c-4-pm-澄清规则"></a>

## 4. PM 澄清规则

PM 只在缺少会实质改变交付结果的信息时提问。能从用户原话和已有 Project Context 得出的信息，不要再问一次。

一次只提一个能推进结果的聚焦问题。如果有多个缺失项，合并成用户可一次回答的问题，不转成问卷。

用户回复后：

1. 回复追加到原 Run 的可见 Context；
2. 原 `input_request` 原子变为 `answered`；
3. 同一 Run 回到 PM 阶段重新判断；
4. 信息仍不足时可以创建下一个 Input Request，但不允许无上限自动循环；
5. 信息足够后创建 Blueprint 或 RequirementDelta，再进入 Risk Policy 和下游执行。

## 能力分级与源码就绪的区别

support_level 判断产品方案是否满足用户已确认范围；source_ready 描述源码交付后的运行结果。缺少 Runtime Adapter 不自动禁止生成源码，也不自动允许把用户要求的运行结果降成源码交付。当前 SourceBundle 和 source_ready 的正式依据见 [Feature 07](../../05-产物与交付部署/07-通用源码与运行校验/01-产品说明.md)。
