# 角色职责与交付物｜产品说明

- Feature：10；适用版本：V1
- 整理日期：2026-09-29；从已有共同基线提取，不新增角色或权限
- 产品依据：[V1 固定团队执行](../../02-任务规划与执行编排/11-固定串行执行/03-执行交互与整体验收.md#p-63-团队负责人lead与固定团队执行)
- 职责依据：[V1 多 Agent 设计](./02-角色契约与上下文.md)

## 背景

用户需要能检查每个角色完成了什么，而不只是看到多个角色轮流发言。本功能定义 V1 团队的专业分工和可阅读、可追溯的交付物；怎样安排执行由编排域负责。

## 摘要

- **专业分工**
  - Lead 接收请求并协调交接；PM 明确产品，Architect 给出技术设计，Engineer 交付源码与测试。
- **结果可检查**
  - 下游使用有效的上游文档；角色自报完成不能替代真实产物、用户确认或运行验证。

## 角色分别交付什么

| 角色 | 负责的问题与结果 | 明确边界 |
| --- | --- | --- |
| 团队负责人（Lead） | 回答、澄清或交接请求，向用户说明团队进度；已有项目修改按专项规则提出修改及入口建议 | 不替专业角色生成其交付物，不直接写代码、执行工具、改变版本或发布 |
| 产品经理（PM） | 保留用户目标、项目类型和目标平台，形成完整产品规格文档；产品蓝图只作为结构化索引 | 不能用短摘要取代产品文档；用户确认当前内容后才可进入下游，能力不足必须明示 |
| 架构师（Architect） | 基于已确认产品文档给出可实现、可验证的架构设计，说明模块、状态与交互、数据与接口、目录和测试策略 | 不重写产品目标，不把配色字体当作完整架构，不虚构运行能力 |
| 工程师（Engineer） | 根据产品和架构设计交付真实源码、单元测试与必要受控配置，并对构建和测试通过负责 | 不擅自改变产品事实，不选择或放宽平台运行规则，不以自报测试成功替代执行证据 |

产品方案的澄清、编辑、失效与重新生成统一见[Feature 02](../02-首次需求澄清与产品方案/01-产品说明.md)。架构设计默认不是第二个强制批准门；如果实现必须改变已批准的产品范围、目标平台、外部能力或高风险权限，应停止下游并重新确认产品，而不是通过架构设计静默批准变更。

工程师的“自测”指交付测试并根据真实失败证据修复，不代表获得宿主终端、平台密钥、数据库、Git 远端或发布权限。构建、测试和校验是平台执行的确定性阶段，不是另外三个模型角色；工程师编写的测试也不能代替平台独立门禁。

V1 不启用 Data Analyst 和 Reviewer 参与新任务，只保留历史产物的只读兼容。重新引入这些角色需要独立产品依据，不因本次建立目录而自动恢复。

## 当前状态与验收依据

共同设计与[Review 23](../../../review/待办/23-[综合]-2026-07-14-多角色职责与交付边界检查.md)保留角色实现和检查记录；本次仅提取产品说明，没有重新执行代码审计、测试或部署验收。PM 编辑与重新生成的剩余差距见 Feature 02，通用源码与运行结果见[Feature 07](../../05-产物与交付部署/07-通用源码与运行校验/01-产品说明.md)，不沿用共同设计中较早的迁移状态覆盖专项现状。

检查本功能时，应能从一个任务中定位产品文档、架构文档、源码与测试，并确认它们对应同一条有效交接链；不能只凭角色消息、阶段动画或目录存在判定完成。
