## 背景

当前已有 Project 的修改 Run 固定执行产品经理（Product Manager）→架构师（Architect）→工程师（Engineer）。即使用户只要求修改一处界面文案或局部样式，系统仍会重新生成需求差量和架构产物。

固定完整链路的合理性在于调度、配额和恢复语义简单；代价是小修改也会支付上游模型调用、更长延迟，并承担本来不需要变化的产物被重写的风险。

本设计不改造整条流水线，只让 Project Lead 多产出一个“从哪个专业阶段开始”的入口。入口之后仍由运行系统（Runtime）执行固定顺序，不引入 TaskGraph、任意角色组合、并行或自动回退。

## 摘要

- **Lead 输出入口**
  - `propose_change` 增加 `entry_stage: product_manager | architect | engineer`。
- **Runtime 执行固定后缀**
  - 产品入口执行产品经理→架构师→工程师；架构入口执行架构师→工程师；工程入口只调用工程师。
- **判断的不是任务名称**
  - Lead 判断本轮修改会使哪一层已确认产物失效；“界面修改”本身不能直接等同于架构入口。
- **上游产物直接复用**
  - 被跳过的角色不调用模型；下游读取当前基线中已确认的产品和架构产物。
- **验证阶段不变**
  - 无论从哪个角色进入，Runtime Build、Unit Test、Validator、基线冲突检查和版本写入门禁都不能跳过。

## 1. 核心决定

### 1.1 只选择入口，不选择整条流程

Lead 总是用户的对话入口。用户批准“修改代码”后，`entry_stage` 决定第一个执行的专业角色：

```text
Project Lead
   |
   +-- product_manager -> architect -> engineer --+
   +-- architect -----------------> engineer ------+--> Runtime Build/Test/Validation
   `-- engineer -----------------------------------+
```

Runtime 只接受这三个入口，并且只能执行图中三个固定后缀。Lead 不输出任务列表、依赖关系、并行组或回退目标。

### 1.2 只用于已有 Project 的修改

首次构建没有可复用的已确认 `ProductSpec`、`Blueprint`、`ArchitectureDesign` 和 `ArchitectureSpec`，因此仍必须从产品经理开始。

只有当 Project 存在有效工作版本和可复用上游产物时，Lead 才能选择 `architect` 或 `engineer`。

## 2. Lead 如何判断入口

判断顺序固定为：

1. 本轮是否需要修改已确认产品需求？
2. 如果产品需求不变，是否需要修改已确认架构设计？
3. 如果两者都不变，则从工程师进入。

如果用户信息不足以判断修改目标，Lead 应返回 `clarify`，而不是用更长流水线代替需求澄清。如果修改目标已经明确，但上游产物是否仍有效存在不确定性，选择更早的入口。

### 2.1 从产品经理进入

适用于修改产品范围、核心能力、业务规则、目标平台、能力边界或验收条件。

- **为什么合理：** 已确认产品产物已不能完整表达用户的新目标，架构和代码不能绕过它直接修改。
- **优势：** 需求、架构和实现仍有明确的上下游关系。
- **代价：** 模型调用和延迟最高；可能重新触发产品范围确认。
- **边界：** 一处界面文案或样式变化不应仅因为“用户可见”就进入产品经理；只有它改变产品语义或验收条件时才属于产品变化。

### 2.2 从架构师进入

适用于产品目标不变，但必须改变模块职责、状态与数据流、接口契约、目录约束、测试策略或其他已记录架构约束。

- **为什么合理：** 产品产物仍然有效，但工程师不能继续按旧架构产物实现。
- **优势：** 避免无效调用产品经理，同时保持架构文档与实现一致。
- **代价：** 比直接调用工程师慢，并且架构师仍可能对原本只需要代码修改的任务做过度设计。
- **边界：** 不是所有布局、交互或视觉修改都从架构师开始。只有它使当前 `ArchitectureDesign` 或 `ArchitectureSpec` 的明确约束失效时，才需要架构入口。

### 2.3 从工程师进入

适用于已确认产品和架构产物都仍然有效，只需要修改实现或测试的任务。

- **为什么合理：** 上游事实没有改变，重新调用产品经理或架构师不会提供新的必要输入。
- **优势：** 调用最少、延迟最低，也避免无关上游产物被重写。
- **代价：** 如果 Lead 判断过晚，工程师可能在未更新上游产物的情况下修改代码。
- **边界：** 局部文案、样式、图标、间距、已有交互缺陷和明确代码错误默认从工程师进入；但它们若同时改变已记录的产品或架构约束，仍要选择更早入口。

## 3. Project Lead 输出

已有 `ProjectLeadDecision` 增加一个可空枚举字段：

```text
ProjectLeadDecision
  intent: answer | clarify | propose_change
  response
  reason
  change_summary?
  entry_stage?: product_manager | architect | engineer
```

字段约束：

- `intent=propose_change` 时，`change_summary` 和 `entry_stage` 必填。
- `intent=answer|clarify` 时，`entry_stage` 必须为空。
- `reason` 记录入口依据：哪层已确认产物需要变化，或者为什么上游产物仍可复用。只保存简短结论，不保存模型私有推理。

`entry_stage` 与 `change_summary`、`base_version_id` 和 Project Context hash 一起写入 pending 修改任务。用户点击“修改代码”时，批准的就是这个绑定了基线和入口的修改任务。修改目标、基线或入口变化后，必须形成新任务，不能继续使用旧批准。

## 4. Runtime 如何执行

### 4.1 校验入口的前置条件

批准修改任务时，Runtime 重新检查：

1. `base_version_id` 仍是 Project 当前有效工作版本。
2. 该入口要复用的上游产物存在，且与基线版本一致。
3. Project 不存在其他正在写入的 Run。
4. 用户批准、配额和 Runtime 能力仍足以执行对应后缀。

如果 Lead 选择 `engineer`，但当前 Project 缺少有效架构产物，Runtime 不能把缺失产物当作“无需修改”。它只能把实际入口提前到能补齐缺失产物的阶段，并记录原因；Runtime 不得自行把入口延后、跳过更多角色。

如果提前入口会导致调用预算超出已批准范围，Run 暂停等待预算确认，不静默增加模型调用。

### 4.2 复用上游产物

- `entry_stage=product_manager`：产品经理生成本轮需求变化，架构师同步架构产物，再交给工程师。
- `entry_stage=architect`：复用当前 `ProductSpec` 和 `Blueprint`，架构师读取修改任务后产出新架构产物，再交给工程师。
- `entry_stage=engineer`：复用当前产品和架构产物，工程师直接读取修改任务和基线源码。

被跳过的角色不得产生本轮模型用量，也不得把旧产物伪装成本轮新输出。运行记录必须能说明哪些阶段被跳过、复用了哪个基线产物。具体是保存 Artifact 引用还是带来源的兼容副本，由实现结合现有恢复机制决定；但必须保留原 Artifact ID/hash 和“本轮未调用该角色”的事实。

### 4.3 验证和版本门禁不改

工程师完成候选修改后，仍执行现有固定阶段：

```text
Candidate Source
  -> Runtime Build
  -> Unit Test
  -> Validator
  -> final base-version check
  -> ProjectVersion + Git commit
```

任一必须检查失败，都不得创建新 ProjectVersion，不改变 Git head 或发布指针。

## 5. 入口判断错误如何处理

V1 不因为增加了入口选择，就同时增加工程师→架构师→产品经理的动态回退。

如果架构师或工程师发现必须改变已跳过的上游产物，当前 Run 不应越权继续；Runtime 保留已产生的证据，终止候选版本，并向 Project Chat 返回“需要从更早阶段处理”。用户确认新修改任务后，再从正确入口创建新 Run。

Runtime 可以确定检查页面清单、路由、视觉 Token、源码范围和已定义字段，但不能仅凭代码 Diff 完整证明“产品和架构语义没有变”。因此该机制的可靠性仍依赖：Lead 保守判断、下游角色不越过本轮任务边界，以及 Runtime 对能显式验证的契约进行门禁检查。

## 6. 用户可见行为

修改任务卡不要求用户自行选角色，但应说明本轮会复用什么：

- 工程入口：“沿用已确认的产品和架构设计，直接修改现有实现。”
- 架构入口：“沿用已确认的产品范围，先同步架构设计，再修改实现。”
- 产品入口：“本轮会改变已确认需求，先整理需求变化。”

运行开始后，Project Chat 和运行日志展示实际入口、当前角色、复用的上游产物和必经验证阶段。如果 Runtime 因为产物缺失而提前入口，必须展示原因，不应让用户从额外等待时间中猜测。

## 7. 为什么这不是 V2 TaskGraph

本设计只有一个枚举入口和三个硬编码后缀：

- 没有可持久化的 Task 节点和依赖边。
- 没有任意角色子集、新角色或多个同角色任务。
- 没有并行调度、分支合并或独立工作区合并。
- 没有基于 Evidence 的跨角色自动返工。
- Lead 不决定权限、预算、工具、重试次数或发布。

V2 改变的是整个执行结构；本设计只是在 V1 固定结构前增加一个入口选择。

## 8. 当前实现差距

1. `ProjectLeadDecision` 尚无 `entry_stage`。
2. pending `change_proposal` 和“修改代码”批准对象没有绑定入口。
3. `_execute_change_run()` 仍固定调用产品经理、架构师和工程师。
4. 架构师和工程师的当前输入要求本轮上游增量产物，尚不支持直接复用基线产物。
5. 当前事件和 Studio 没有表达“本轮跳过哪些角色、复用哪些产物”。
6. 当前 Validator 尚无针对“修改超出所选入口”的完整检查。

## 9. 实施顺序

1. 在 Contract 中新增 `ChangeEntryStage` 和 `ProjectLeadDecision.entry_stage`，同步 Mock 与真实 Provider。
2. 调整 Project Lead 指令，让它根据当前 ProductSpec、架构产物、源码和用户修改要求选择入口。
3. 在 pending 修改任务、批准事务和 Run 中保存入口及其基线。
4. 将修改 Orchestrator 拆成三个固定进入分支，共用工程和 Runtime 验证后缀；不引入 TaskGraph 表或通用调度器。
5. 调整架构师和工程师输入，允许本轮没有 `RequirementDelta` 或新架构产物时，直接使用已确认基线产物。
6. 增加跳过阶段、产物复用、入口提前和入口过晚的事件及 Studio 反馈。
7. 完成本地自动化测试和 Railway 真实 Provider 验收后，再更新实现与验证状态；文件名保持稳定。

本节仅说明已有方案的实施顺序。进入代码开发前，仍须核对并确认本专项技术设计，再派生和确认 Code Spec；本次产品确认不替代这些门禁。

## 10. 验收标准

- 首次构建仍从产品经理开始，并执行完整三角色链路。
- 已有 Project 的局部界面文案、样式或明确代码错误可以输出 `entry_stage=engineer`，本轮不调用产品经理和架构师。
- 只改变架构产物明确约束的修改可以输出 `entry_stage=architect`，本轮不调用产品经理。
- 改变产品范围、业务规则或验收条件的修改输出 `entry_stage=product_manager`。
- 被跳过的角色不产生本轮模型用量；运行记录可追溯复用产物的 Artifact ID/hash。
- 基线、修改目标或入口变化后，旧批准失效；重复批准同一任务不创建多个 Run。
- 缺少必要上游产物时，Runtime 只能提前入口并记录原因；发现入口过晚时不在同一 Run 中自动跨角色回退。
- 三种入口都执行 Runtime Build、Unit Test、Validator 和最终基线检查；失败时不创建 ProjectVersion，不改变 Git head 或发布指针。
