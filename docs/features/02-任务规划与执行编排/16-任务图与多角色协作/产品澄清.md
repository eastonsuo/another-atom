## 背景

用户希望考虑“先 plan 后执行”，旧草案也已有任务图（TaskGraph），但“生成计划”和“用户批准计划”不是同一件事。旧正常路径写的是运行系统（Runtime）校验后调度，同时又使用 `task_graph_approved` 事件名，没有明确这是否表示人工批准。本次用户选择由 AI 判断、仅在必要时确认，不把计划生成本身设为固定人工门禁。

## 摘要

- 当前产品规格确认与越权、预算、范围变更确认已经有明确规则，不重开这些决定。
- 已确认不为每份 TaskGraph 增加一次独立的用户门禁：已确认范围内正常推进，需要用户补充信息、作出取舍或追加授权时才暂停相关执行。
- AI 识别必要澄清／确认，Runtime 保留权限、预算及有效批准等强制校验；AI 判断不替代用户授权或确定性校验。

## PQ-03：产品规格已经确认，任务计划生成后还要再点一次“执行”吗？

**已有依据**：[产品说明](./01-产品说明.md)的 Autonomous Team Execution、正常路径与产品事件，以及[协作状态草案](./03-持久化调度与协作状态.md)的 TaskGraph 与调度。它们要求图可见、Runtime 校验和产品／风险确认，但未定义独立计划确认的完整规则。尚无 V2 实现可以作为结果证据，更不能用事件名倒推用户需求。

**当时提供的选择**：

| 选择 | 用户得到什么 | 代价与边界 |
| --- | --- | --- |
| A：每次计划都先确认 | 图和执行范围展示后，用户点“执行”才开始 | 多一次操作；后续图重排、局部返工是否重新确认还需明确 |
| B：有效产品范围内自动执行 | 用户可检查计划，Runtime 校验通过后推进；范围、预算或权限变化仍暂停确认 | 普通计划不增加操作，但用户没有固定的逐份计划批准窗口 |

当时没有代选默认值。用户现已明确按需确认，与 B 的执行方向一致，并补充由 AI 主动识别需要介入的情形。该答复只确认计划开始和变更的产品行为，不改变首次产品规格（ProductSpec）确认或已有项目修改的固定入口。

**用户原始回复**：

> 这个是不是AI判断，仅在必要时进行确认吧

- 确认人：项目负责人（用户）。
- 确认日期：2026-09-29。
- 回复来源：本次对话中，用户对“产品需求已经确认，Agent 生成执行计划后是否还需确认”的 A／B 选择段落所作的批注；不是对所有产品或风险确认的取消。

**归一化结论**：

1. 不要求用户对每份计划再点击一次“执行”。计划可查看；产品需求和授权仍有效、计划处于已确认范围内且通过 Runtime 校验时，自动进入执行。
2. AI 负责识别计划中的需求歧义、必要信息缺口或需要用户取舍的变化，并在必要时提出具体问题、影响和所需决定。缺少信息时先澄清，不把信息回复混同于风险授权。
3. 范围变化、追加预算、需要新增且平台允许授予的工具／依赖／网络权限、破坏性变更和无法仲裁的冲突，沿用已有确认规则。Runtime 必须执行相应约束，不能仅因 AI 没有请求确认就放行；跨用户访问、不支持的能力和 mandatory 校验失败也不能通过用户确认豁免。具体边界继续以 [Feature 03](../../03-用户交互与协作/03-人工确认与流程恢复/01-产品说明.md) 和 [Feature 17](../../04-执行与验证环境/17-任务级隔离与受控工具/01-产品说明.md) 为准。
4. 计划重排或局部返工本身不新增固定确认，仍按是否改变已确认范围、预算、权限或具体确认对象判断。同一有效对象已有确认且后果未扩大时不重复询问，对象变化后不能沿用失效批准。
5. 首次 ProductSpec 确认、已有项目修改任务批准和手动发布／更新规则不变。AI 判断“无需额外计划确认”不等于批准上述独立动作。

**回写与剩余工作**：本 Feature 产品说明已补充计划自动推进、按需确认及验收要求；任务图和调度草案只同步该产品约束，关联文档引用同一结论。AI 判断结果如何持久化、如何连接澄清／审批与恢复，以及旧 `task_graph_approved` 事件的命名和证据语义，仍须技术设计和 Code Spec 明确，不能把事件名当成用户已批准。

**当前状态**：本项产品选择已确认并回写；尚未实施或验证。V2 的整体范围、SDK、Sandbox Provider、预算上限等仍按各自门禁处理，本答复不同时批准它们。
