<a id="vp-1-版本结论"></a>

## 1. 版本结论

V2 在 V1 可部署闭环上实现**受 Runtime 约束的自主多 Agent 协作**：V1 的 Lead 从回答／澄清／固定团队路由演进为 TaskGraph 协调者；Product Manager、Architect、Engineer、Data Analyst、Reviewer 使用独立 Context 完成任务，通过 Handoff 交付；Engineer/Data Analyst/Reviewer 可以在 Run 级 Sandbox 内申请受控 Tool，失败时依据 Evidence 进行有预算的返工与收敛。

```text
V1: Lead 回答／澄清／固定团队路由
User -> Lead -> direct / clarify / PM -> 产品确认 -> Architect -> Engineer -> Runtime Build/Test/Validator

V2: Runtime 约束的自主多 Agent
User -> Lead -> direct | TaskGraph
                         |
             +----------------+----------------+
             v                v                v
       Product Manager     Architect        Engineer <-> Data Analyst
             |                |                |          |
             +------ Artifact / Handoff -------+          v
                                                   Validator -> Reviewer
                              |
                       Version / Publish
```

V2 是计划实施版本，不是已经完成的能力。实施顺序固定为 V1 -> V2。

<a id="vp-2-要解决的问题"></a>

## 2. 要解决的问题

V1 的固定 Pipeline 适合验证闭环（已有项目三个固定入口是已确认但尚未实现的产品方向），但存在明确边界：

- Lead 判断为 `team` 后，首次创建按完整三角色执行，已有项目修改可按已确认产品基线选择固定后缀；仍不支持任意角色组合、依赖图和并行。
- Agent 只产生结构化 Contract，没有文件、构建、测试和浏览器 Tool，无法处理更真实的实现与修复任务。
- 自动修复最多一轮，只能回到 Engineer，无法把规格、视觉或需求根因路由给责任角色。
- 所有角色按顺序运行，架构设计与独立数据准备等无依赖任务也不能并行。
- V1 只有阶段级 Context，无法验证独立 Agent 的 Handoff、拒收、仲裁和预算治理。

V2 需要增加自主性，但必须保留 V1 已证明有效的风险驱动确认、Artifact Contract、用户级隔离、Project 本地 Git、确定性 Validator、版本历史和用户显式 Publish。

<a id="vp-3-产品目标"></a>

## 3. 产品目标

本组详细条款见 [01-产品说明](./01-产品说明.md)。

<a id="vp-31-要验证的判断"></a>

## 3.1 要验证的判断

1. Leader 生成的 TaskGraph 是否能比固定 Pipeline 更准确地匹配任务复杂度。
2. 独立 Context + Handoff 是否能让角色交付可检查，而不是退化为多 Agent 聊天。
3. 受控 Tool + Run 级 Sandbox 是否能提高真实实现和修复能力，同时维持隔离边界。
4. Evidence 驱动的 Rework/Arbitration 是否能在预算内收敛，而不是无限返工。
5. 并行分支、配额、部分失败和恢复是否能形成可交付的多用户系统。

<a id="vp-32-不在-v2-p0-验证的判断"></a>

## 3.2 不在 V2 P0 验证的判断

- 不把“接受任意软件产品目标”夸大为任意代码都能直接执行。V2 延续按项目类型选择 Source/Build/Runtime Adapter 的边界；没有适配器的项目仍可保留目标和源码，但不能声称已经可运行或可预览。
- 不把 CC 式本地 Agent Runtime 自动并入 V2；是否同版本交付需单独确认。
- 不实现无人审批的任意代码执行、外部依赖安装或开放网络访问。
- 不实现 Agent 自动 Publish、自动提高预算或绕过用户确认。
- 不展示模型私有 Chain of Thought。

## 4.1 目标用户

- 需要把产品需求变成可持续管理的软件项目，并希望检查规划、设计、实现和测试依据的用户；网页项目可额外使用浏览器 Preview。

<a id="vp-42-v2-相对-v1-的用户价值"></a>

## 4.2 V2 相对 V1 的用户价值

| V1 | V2 用户可感知变化 |
| --- | --- |
| 固定角色时间线 | 可查看由真实依赖生成的 TaskGraph、并行分支和当前责任角色 |
| 阶段顺序交接 | 每次 Handoff 有 Artifact、Evidence、接受/拒绝和原因 |

<a id="vp-5-产品原则"></a>

## 5. 产品原则

1. **自主不等于越权**：Agent 提建议和 ToolRequest，Runtime 执行权限、配额、并发和状态硬规则。
2. **交付物优先**：没有 Artifact/Evidence 的 Agent 消息不构成阶段完成。
3. **用户门禁继承 V1**：supported 与 adapted 均继承 V1 的 ProductSpec 固定确认；范围变更、越权 Tool、预算追加、破坏性操作和 Publish 必须由用户确认。
4. **确定性验收优先**：Reviewer 不能覆盖 Build/Test/Validation 的 mandatory 结果；Data Analyst 不承担最终验收职责。
5. **有预算地收敛**：每个 Run 有调用、token、时间、并发和 Artifact 修订上限。
6. **V1 可回归**：V2 的数据、事件和 UI 扩展不能破坏 V1 ProjectVersion、Publish 和公开 URL 语义。

<a id="vp-61-autonomous-team-execution"></a>

## 6.1 Autonomous Team Execution

- 用户仍只面对 Lead，不新增必须理解的模式选择器。Lead 可以 direct，也可以提出 team TaskGraph；用户可显式要求“调用团队”。
- Product Manager 先产生 Blueprint。supported 与 adapted 的 ProductSpec 均先由用户确认，随后才可进入 TaskGraph；adapted、范围变化或预算超出基础额度时先触发 Risk Policy。
- Leader 基于当前有效 Blueprint 生成 TaskGraph，Runtime 校验依赖、角色、预算和允许的并行组。
- TaskGraph 必须可视化，显示节点、依赖、状态、Agent、Artifact 和 Evidence，不展示私有推理。

计划生成不额外增加一次固定“执行”确认。AI 识别是否缺少必要信息、存在需要用户取舍的歧义，或会改变已确认范围、预算、权限与高影响后果：普通计划在授权有效且 Runtime 校验通过后自动执行；确需用户介入时，说明具体问题和影响并暂停相关执行。Runtime 的强制约束不依赖 AI 是否主动请求确认，禁止事项和 mandatory 校验失败不能通过确认豁免。首次 ProductSpec、已有修改任务及发布的独立确认不变，依据为 [PQ-03](./产品澄清.md#pq-03)。

<a id="vp-63-context-与-handoff"></a>

## 6.3 Context 与 Handoff

- 每个 Agent 使用独立 Context，只接收当前 Task 所需的 Artifact、Evidence、Tool Observation 和预算摘要。
- 角色之间只能通过 Handoff Package 交接，不共享隐藏长期记忆或原始 Chain of Thought。
- 接收方可以 Accept 或 Reject；Reject 必须包含 Contract violation、Evidence 和建议责任角色。
- Artifact 不原地覆盖，返工产生新版本并保留 parent/correlation 关系。

<a id="vp-65-选择性并行"></a>

## 6.5 选择性并行

- Runtime 只并行执行 TaskGraph 中无依赖冲突、无共享写入且预算已预占的节点。
- 第一条并行路径限定为 Architect 与 Data Analyst 中已被 Runtime 判定无依赖、无共享写入的架构/数据准备子任务。
- UI 显示并行分支、各自状态、消耗和 Handoff；不能用同时闪动角色头像伪装并行。
- 任一分支失败不自动回滚已成功分支的 LLM 用量或 Artifact；失败分支按策略重试、降级或请求用户。

<a id="vp-66-reworkarbitration-与收敛"></a>

## 6.6 Rework、Arbitration 与收敛

- Reviewer 或下游接收方基于 Evidence 生成 ReworkRequest，Runtime 按 root cause 路由给责任角色。
- Agent 不能点对点私聊；所有请求通过 Runtime 和持久化 Handoff。
- Leader 可以提出 ArbitrationDecision，Runtime 校验 Blueprint、权限和预算后执行。
- 达到 Artifact 修订、Agent 调用、token、时间或相同 Evidence 重复上限后停止，保留最近可用 Version。
- 需要改变 Blueprint 范围、追加预算或越权 Tool 时必须进入 Human-in-the-loop。
- 计划重排或局部返工本身不要求重新批准整份计划；仍按第 6.1 节检查是否出现必要澄清或新的确认事项。同一有效对象且后果未扩大时不重复确认，对象变化后不得复用失效批准。

<a id="vp-67-预算配额与部分失败"></a>

## 6.7 预算、配额与部分失败

- 每个 Run 在执行前创建 RunBudget，包含调用、token、deadline 和并发上限。
- 并行分支启动前，父 Run 原子预留可覆盖所有子任务的额度，再分配子预算。
- 子任务成功后按实际用量结算；失败/取消只释放未使用预留，已经发生的 Provider/Tool 用量不能回滚。
- 一支成功、一支失败时，成功 Artifact 保留为可复用输入；Leader/Runtime 决定重试失败分支、取消未启动分支或请求用户。
- UI 展示预算消耗和停止原因，但不展示内部价格推理或模型 Chain of Thought。

<a id="vp-68-reviewer版本与发布"></a>

## 6.8 Reviewer、版本与发布

- mandatory Build/Test/Validation Evidence 仍由确定性系统产生，Reviewer Agent 不能改写。
- DataProfile 描述应用数据事实；ReviewReport 提供用户可读结论、Evidence 链接、warning 和 Rework 建议。
- 合并到 ProjectVersion 前，候选 Artifact 必须通过 Contract、Build、Test、安全和 mandatory checks。
- Restore、工作版本与线上版本分离、显式发布／更新沿用 [Feature 12 的 V1 规则](../../05-产物与交付部署/12-版本预览与发布/02-版本预览与发布规则.md#p-67-发布与分享)，不因引入多角色协作恢复自动上线选项。
- Publish/Update/Unpublish 仍由用户显式操作，Leader 和 Specialist 都不能自动发布。

<a id="vp-7-核心用户旅程"></a>

## 7. 核心用户旅程

本组详细条款见 [01-产品说明](./01-产品说明.md)。

<a id="vp-71-正常路径"></a>

## 7.1 正常路径

1. 用户向 Lead 输入 Mono Market Prompt；Lead 路由到 team，Product Manager 生成 ProductSpec 与 supported Blueprint，由用户确认当前产品规格。
2. Leader 提交 TaskGraph，并识别是否需要用户补充信息或确认变化；无此类待处理事项且 Runtime 校验通过后，展示任务与预算并自动推进，不再等待一次固定“执行”确认。
3. Architect 与 Data Analyst 的数据准备任务在允许条件下并行，分别交付 ArchitectureSpec 与 DataProfile。
4. Engineer 接收已接受的 Handoff，在 Sandbox 内修改、构建和测试。
5. 确定性 Validator 生成 ValidationEvidence，Reviewer 在只读快照上独立复核并交付 ReviewReport。
6. mandatory checks 通过且 Reviewer 接受后生成 ProjectVersion，用户预览并显式 Publish。

<a id="vp-72-返工路径"></a>

## 7.2 返工路径

1. Reviewer 引用 ValidationEvidence 指向 implementation failure，生成 ReworkRequest。
2. Runtime 校验 root cause 和预算，路由给 Engineer。
3. Engineer 基于原 Artifact 新建修订，重新 Build/Test。
4. Validator 复验，Reviewer 再次审查；成功则合并，达到预算则停止并请求用户。

<a id="vp-73-human-in-the-loop-路径"></a>

## 7.3 Human-in-the-loop 路径

出现以下任一情况时暂停：adapted/范围变化、越权依赖或网络、追加预算、无法仲裁冲突、破坏性仓库操作、Restore/Unpublish/Publish。用户批准只绑定精确 Artifact/ToolRequest/Budget version；对象变化后旧批准失效。

<a id="vp-8-工作区与界面"></a>

## 8. 工作区与界面

V2 在 V1 Studio 上增加：

- TaskGraph：任务依赖、并行分支、当前 Agent 和状态。
- Agent Inspector：role、Task、输入/输出 Artifact、ToolRequest、Usage 和 Trace 摘要。
- Handoff Panel：Accept/Reject、Contract violation 和 Evidence。
- Evidence Panel：Build/Test/Browser/Screenshot 结果，不展示 Chain of Thought。
- Approval Center：范围、Tool、预算和发布等待项。
- Budget Bar：已预留、已结算、剩余和停止原因。
- Rework/Arbitration Timeline：返工来源、责任角色、版本差异和 Leader 建议。

移动端不同时展开 TaskGraph、Inspector 和 Preview，使用单区域切换，避免压缩成不可操作的桌面布局。

<a id="vp-9-状态模型"></a>

## 9. 状态模型

```text
Run
Created -> LeadRouting -> Planning -> Running
                                               |       |
                                               |       +-> AwaitingRiskApproval
                                               |       +-> Reworking
                                               |       +-> PartiallyFailed
                                               v
                                          Validating -> Completed
                                               |
                                               `-> Failed / BudgetExhausted / Cancelled

Task
Pending -> Ready -> Reserved -> Running -> Completed
                    |            |          |
                    v            v          `-> ReworkRequested
                 Cancelled     Failed

Handoff
Created -> Delivered -> Accepted
                    `-> Rejected -> ReworkRequested
```

<a id="vp-10-p1-候选范围"></a>

## 10. P1 候选范围

- 扩展到更多应用类型和对应 Capability Policy/Renderer。
- 多候选实现竞速与自动选择。
- 用户可配置模型 Provider 和每角色模型。
- 更复杂的并行图和多 Engineer 分支合并。
- 视觉截图自动评分和可访问性深度测试。
- CC 式本地 Runtime 与云端 TaskGraph 协同。
- 团队成员审批、评论和共享预算。

这些能力不阻塞 V2 P0，多应用类型和 Local Runtime 必须单独确认产品与安全边界。

<a id="vp-11-明确不做"></a>

## 11. 明确不做

- 不允许 Leader 或 Specialist 绕过 Runtime 直接执行宿主机 Shell、数据库或 Publish。
- 不在没有 Run 级隔离时执行模型或用户提供的任意代码。
- 不共享 Agent 私有 Chain of Thought，不用聊天瀑布替代 Artifact/Evidence。
- 不自动扩大 Blueprint 范围、追加预算、批准依赖或开放网络。
- 不承诺无限返工、无限 Context 或无限并发。
- 不把 V2 P0 描述为已经具备全部 Build/Runtime Adapter 的通用代码执行平台。

<a id="vp-12-验收标准"></a>

## 12. 验收标准

本组详细条款见 [01-产品说明](./01-产品说明.md)、[01-产品说明](../../04-执行与验证环境/17-任务级隔离与受控工具/01-产品说明.md)。

<a id="vp-121-功能验收"></a>

## 12.1 功能验收

- V1 Golden Path、版本及手动发布／更新规则回归通过。
- Lead 的 autonomous team 路径真实生成并持久化 TaskGraph、Task、Artifact、Handoff、ToolRequest、Evidence 和 RunBudget。
- 至少一条无依赖分支真实并行执行，并能从事件时间与独立 Task 状态验证。
- 至少一条 Evidence 驱动 Rework 路径能路由、修订、重建、复验并收敛。
- adapted/范围变化、越权 Tool、预算追加、破坏性仓库操作和 Publish 的 Human-in-the-loop 均不能被 Agent 绕过。
- mandatory failure 不能被 ReviewReport 或 LeaderDecision 改写为通过。
- Publish 只接受已通过门禁的 ProjectVersion 和用户显式请求。
- 已确认范围内且校验通过的计划直接执行；计划重排、局部返工不因发生本身重复询问用户。
- AI 识别到必要信息缺口或用户取舍时，展示具体问题；命中范围、预算、权限或破坏性变化的确认规则时，相关动作在确认前不执行。AI 未提示也不能绕过 Runtime 强制约束。
- 同一有效对象不重复确认，对象变化后旧批准失效；计划自动推进不能跳过 ProductSpec、修改任务批准或手动发布要求。

<a id="vp-123-重复运行基线"></a>

## 12.3 重复运行基线

- V2 Golden Path 在干净数据下连续完成 5/5。
- 预期 Task/Agent/Handoff/Tool 事件关联完整率为 100%。
- 跨 Project/Run/Agent Context 串线数量为 0。
- 达到预算或收敛上限后继续调用模型/Tool 的数量为 0。

<a id="vp-13-产品事件与价值判断"></a>

## 13. 产品事件与价值判断

V2 在 V1 漏斗上新增：

```text
task_graph_approved
parallel_branch_started
handoff_accepted
handoff_rejected
tool_request_executed
rework_started
rework_converged
arbitration_requested
budget_exhausted
```

`task_graph_approved` 是旧草案事件名，不据此设置逐份人工审批，也不能把 Runtime 校验放行统计成用户批准。事件命名以及系统放行、必要人工确认的证据区分，仍待技术设计与 Code Spec 核对；本次不新增事件协议。

没有真实样本前不预设“并行更快”或“多 Agent 成功率更高”。必须先采集总完成时间、串行/并行资源消耗、Handoff 拒绝率、Rework 收敛率、每个成功 Version 的调用/token/Tool 成本，再判断 V2 是否优于 V1。

<a id="vp-14-风险与取舍"></a>

## 14. 风险与取舍

- 多 Agent 可能增加成本而不提高结果质量；必须用 Artifact/Evidence 和 V1 对照验证。
- 并行缩短墙钟时间，但会增加配额事务、部分失败和资源峰值复杂度。
- Tool 提高实现能力，同时扩大文件、依赖、网络和 Secret 风险；Run 级 Sandbox 是上线前置条件。
- Leader 可能成为新的单点推理瓶颈；Runtime 必须能拒绝无效 TaskGraph 并提供确定性降级。
- Context/Handoff 过度压缩会丢信息，过度传递又会导致成本和污染；必须记录 Artifact 版本和 Evidence。

## 15. 开发前待确认

- 具体模型供应商、Agent SDK 和 Prompt 版本策略。
- Run 级 Sandbox 采用容器、MicroVM 还是远程 Sandbox 服务。
- 网络 allowlist、依赖白名单和 Secret Broker 实现。
- 各 Agent/Artifact 修订、总调用、token、并发和 deadline 的压测上限。
- Data Analyst 是否在 P0 使用视觉截图评估，以及对应测试集。
- V2 P0 首批新增哪些非 Web Source/Build/Runtime Adapter，以及各自的安全与验收边界。
- V2 是否与 CC 式 Local Runtime 同版本交付。
