## 背景

用户要求生成什么类型的软件，与平台当前能在线运行什么类型的软件，是两件不同的事。不能为了让 Preview 成功，把非 Web 项目改成网页，也不能因为暂时没有运行环境就否认已经形成的源码交付。

本功能明确源码、运行能力和交付结果之间的关系，使用户能知道自己拿到了什么、实际验证了什么、还有什么没有完成。

## 摘要

- **项目身份不变**
  - 按用户目标交付源码；Preview 是匹配运行能力后的附加结果，不是生成范围的上限。
- **规则前置且一致**
  - 工程师生成前看到的运行约束，与后续真实校验使用的约束一致；系统不能在后段突然增加隐藏规则。
- **结果如实区分**
  - 可运行、仅源码就绪、候选被拒绝和执行受阻各有明确含义；失败不覆盖最后可用版本。

## 1. 源码交付范围

源码包（SourceBundle）保存项目真实文本源码，可以包含入口、测试、配置和文档，不固定为 HTML/CSS/JavaScript 三个文件。交付元数据不能反过来重建、改写权威源码。

用户可以查看源码、产物和版本，并使用已有导出能力。平台缺少对应工具链时，必须说明尚未在线构建、测试或运行的部分，不能声称程序已经可用。依赖、网络、服务端认证、数据库和外部服务等缺口也必须明示。

## 2. 用户能拿到什么

| 结果 | 用户含义 | 版本与预览后果 |
| --- | --- | --- |
| 可运行（`valid`） | 源码有效，并通过所选运行能力要求的实际检查 | 可以形成工作版本；Preview/发布仅在该项目确有对应能力时提供 |
| 源码就绪（`source_ready`） | 源码通过通用检查，但没有绑定可执行运行能力 | 可以形成源码版本、查看和导出；明确不宣称在线构建、测试、Preview 已通过 |
| 候选被拒绝（`candidate_rejected`） | 当前候选源码或执行结果不满足合同 | 保留错误和候选证据；不移动最后可用版本、Git 基线和发布指针 |
| 执行受阻（`execution_blocked`） | 安全、权限或执行条件不允许继续 | 说明阻断原因；不能通过降低校验或用户审批冒充可运行交付 |

首次生成没有成功版本时，也应保留失败证据，不能显示 Ready。用户可以依据具体错误继续调整；已有项目失败后仍以最后成功版本为基线。

## 3. 校验承诺与边界

系统依次检查通用源码有效性、与所选运行能力的兼容性以及真实执行结果。路径、大小、内容一致性属于通用检查；语言、入口、依赖、网络和工具链由具体运行合同决定。通用检查通过不等于所有语言已经编译通过。

产品质量建议与强制验收条件分开呈现。非阻断警告不能冒充致命错误；真正影响安全、完整性和明确验收条件的失败也不能为了提高通过率降为警告。

历史 Web 版本保留只读兼容；新 Web 生成采用完整 HTML 文档和真实文件布局，运行时的 Preview 保护不能改写仓库中的业务源码。

## 4. 验收与质量目标

1. 同一请求的产品类型在需求、源码、版本和结果说明中保持一致。
2. 有运行能力时提供匹配本次源码的真实执行证据；无运行能力时不伪造 Preview。
3. 失败候选保留可定位的阶段、文件与错误，不破坏原版本。
4. 工程师、预检、执行和界面使用同一版本的运行规则；历史版本仍可按原合同读取。

既有设计中的 90% 是按项目类型和运行合同统计的首次候选质量目标，不是已达到的指标。首次成功、修正后成功和仅源码交付必须分别统计，不能靠缩小产品目标或放松校验达标。
