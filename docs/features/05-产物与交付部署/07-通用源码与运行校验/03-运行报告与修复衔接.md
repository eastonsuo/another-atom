## 2.6 运行系统构建、测试与校验器（Runtime Build、Test 与 Validator）：生成不可由智能体（Agent）改写的工程证据

**职责：** 构建工作器（Build Worker）、测试运行器（Test Runner）和校验器（Validator）都不是大语言模型（LLM）角色。运行系统（Runtime）校验 SourceBundle 中由主服务绑定的 Runtime Contract，再由满足该 Interface 的 Adapter 在隔离沙箱（Sandbox）内物化源码包，执行平台固定的构建和单元测试计划，并独立检查产品规格（ProductSpec）、架构设计（ArchitectureDesign）、交付规格、源码包和真实运行证据是否一致。没有 Runtime Binding 的有效源码进入 `source_ready`，不伪造在线执行证据。

**输出一：** 执行报告（`ExecutionReport`）。

| 字段 | 含义 |
| --- | --- |
| `source_manifest_hash` | 本次执行对应的源码包（SourceBundle）指纹 |
| `adapter_id` | 实际使用的固定适配器（Adapter） |
| `build_status` | 构建通过、失败或不适用 |
| `test_status` | 单元测试通过、失败或不适用 |
| `test_summary` | 测试数、通过数、失败数和耗时 |
| `evidence_refs` | 构建日志、测试日志和可定位失败的证据引用 |

**输出二：** 校验报告（`ValidationReport`）。

| 字段 | 含义 |
| --- | --- |
| `passed` | 所有 mandatory check 是否通过 |
| `checks` | 每项确定性检查的状态、根因、可修复性、详情和证据引用 |
| `source_manifest_hash` | 本次校验对应的源码包（SourceBundle）指纹 |
| `execution_report_ref` | 被校验的执行报告（ExecutionReport）引用 |

强制检查（mandatory check）至少包含：产品验收条件映射、架构模块与入口交接、源码完整性、单元测试存在与真实执行结果、能力边界、网络和安全约束。只有全部失败都属于工程师（Engineer）可修复的源码或测试问题时，运行系统（Runtime）才进入一次自动修复；适配器（Adapter）、沙箱（Sandbox）、平台或不明根因不得用智能体（Agent）重写源码来掩盖。

<a id="a-81-谁拥有验收权"></a>

## 8.1 谁拥有验收权

```text
Build Worker             -> 是否成功构建
Test Runner              -> Engineer 交付的单元测试是否真实通过
Deterministic Validator  -> 产品、架构、安全和能力 mandatory checks 是否通过
Engineer                 -> 根据真实失败证据修改源码或单元测试
User                     -> 是否接受、继续修改或发布
```

Engineer 对构建和单元测试通过负责，但不能给自己的输出直接判定通过。只有 Runtime 生成的 ExecutionReport 和 ValidationReport 构成工程通过证据；任何修复都必须重新经过所选运行合同要求的 Build、Test 和 Validation；无运行绑定的源码版本遵循 source_ready 规则，不伪造执行证据。

<a id="a-83-自动修复输入输出"></a>

## 8.3 自动修复输入输出

首次创建的自动修复最多一轮。输入必须包含有效 ProductSpec、ArchitectureDesign、当前候选 SourceBundle（含相关测试）及可定位失败证据；输出是新的独立修订产物。SourceBundle 的内容和指纹改变后，不能复用旧执行报告作为通过依据。

Runtime 对修订候选重新执行适用的源码、运行兼容、Build/Test/Validation 检查；精确字段和状态统一见 [本 Feature 技术总设计](./02-技术总设计.md)。不再使用“从 AppSpec 三字段重新渲染源码”作为通用修复链路。

仍失败、根因属于平台／适配器，或需要改变已批准产品与架构时停止并保留证据，不自动跨角色回退。已有项目修改的修复上限与流程见 [Feature 04](../../02-任务规划与执行编排/04-对话式代码修改/02-技术总设计.md)，不能把首次创建的一轮限制误套到所有修改。

<a id="s-55-运行时适配器runtime-adapter与预览沙箱preview-sandbox"></a>

## 5.5 运行时适配器（Runtime Adapter）与预览沙箱（Preview Sandbox）

本节只保留系统级关系；通用 Source Contract、版本化 Runtime Contract、校验分层、结果状态与 Web 兼容迁移以[通用源码与 Runtime 校验 Contract](./02-技术总设计.md)为事实来源。

本功能不按商品类型选择预制渲染器（Renderer）。工程师（Engineer）生成真实源码包（SourceBundle）与交付规格，运行系统（Runtime）校验主服务绑定的 Runtime Contract，并由满足该 Interface 的已登记 Adapter 负责确定性物化、构建、测试，以及 Contract 支持时的隔离预览：

- 只接受通过模式（Schema）校验且指纹一致的应用规格和源码包。
- 适配器声明允许的目录、入口、固定构建/测试命令和预览能力；源码包不能自带任意执行命令。
- 历史网页适配器（Web Adapter）兼容路径曾只向当前项目 Git 写入 `index.html`、`styles.css`、`app.js`、`app-spec.json` 和版本标记；这不是当前通用源码契约的文件上限，当前实现核对见本 Feature 产品说明。
- 当前 `web-static-v1` 兼容路径把 HTML 解释为语义化 body Fragment；交互代码位于 JavaScript 字段，不能在 HTML 中夹带 script/iframe/object/embed。该规则不是通用 Source Contract，新的完整 Document Web Contract 使用独立标识，不复用含义模糊的 `html` 字段。
- 允许公网 HTTP(S)/WS(S) API 请求；禁止 localhost、127/8、`::1`、`0.0.0.0` 和用户设备本地服务。远程可执行资源、dynamic import、eval、运行时依赖安装和模型提供的命令字符串仍禁止。
- Preview 使用 `sandbox="allow-scripts"` 且不授予 `allow-same-origin`；CSP 只为 `connect-src` 开放 HTTP(S)/WS(S)，外部脚本、字体、媒体和表单提交仍关闭，并在 Preview 与物化 `app.js` 中安装 loopback 请求 Guard。
- 同一个源码包（SourceBundle）必须物化为语义一致的源码文件；绑定 Runtime Contract 的候选在构建、单元测试或强制校验失败时不得创建项目版本（ProjectVersion）。没有 Runtime Binding 的有效源码可以形成 `source_ready` 源码版本，但不能展示伪造的 Build/Test/Preview 证据。

旧结构化编辑的 AppSpec 兼容路径不定义通用源码修改语义；新的修改以 SourceBundle 为源码事实源，并重新取得适用校验证据后才形成版本。受限 Vim 的任意源码编辑仍要求独立 Linux Sandbox Host。
