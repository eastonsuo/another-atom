## 背景

用户需要持续修改已经生成的项目，并明确区分当前编辑内容、保存版本和线上内容。生成完成不等于已经发布；一次修改或发布失败也不能破坏最后可用结果。

## 摘要

- **版本可追溯**
  - 查看和恢复已有版本，保留历史及来源，不用重跑任务代替恢复。
- **交付状态清楚**
  - 预览依赖项目运行能力；导出与源码就绪不能冒充已在线运行。
- **线上变更明确**
  - 发布策略决定保存是否更新线上，界面同时说明当前版本与线上版本。

## 版本与恢复

首次成功构建形成首个版本，后续明确保存形成新版本，记录时间、摘要、来源及 Git 提交。版本历史属于 Project，不因最新任务执行中、失败、等待输入或取消而消失；没有版本时入口应解释为何不可用。

用户可以只读查看历史版本。恢复历史版本会创建新的当前版本并保留原历史，不覆盖或删除旧提交。对于当前可运行版本的恢复，必须依据既有验证记录重新通过当前适用验证，成功后才形成恢复版本；恢复不会自动发布或改变公开版本指针。

失败页的“重试”与“回到上个可用版本”不同：前者重新执行任务，后者依据历史候选及实际验证恢复可用结果。两者都不能把失败证据删除或把未经检查的历史版本当成可用结果。Remix 则从所选版本建立独立项目，保留来源关系，后续修改互不影响。

刷新后项目、版本和当前编辑状态应保持。项目版本与 Git 提交一一对应，不通过强制重置、变基或删除旧提交改写历史；是否允许候选形成版本统一由 Feature 07 的结果规则决定。

## 预览和导出

有匹配运行能力的项目展示真实生成结果，而不是静态截图或与需求无关的模板；Web 预览支持桌面／移动两种尺寸、刷新和新标签打开。进度、日志与失败说明应来自实际执行。文本和源码编辑的独立规则见[Feature 05](../../03-用户交互与协作/05-项目文本文件阅读与编辑/01-产品说明.md)。

无匹配运行能力的项目可以按 Feature 07 保留源码、文档和版本，并使用已有导出能力；不得把源码就绪说成已经在线构建、测试、预览或部署成功。

V1 提供版本化 JSON 导出，精确格式由本 Feature 的[发布规则](./02-版本预览与发布规则.md)维护，技术侧只定义持久化和安全边界。导出不包含密钥、凭证、绝对存储路径、原始对话或内部配额流水；静态源码 ZIP 不属于当前 P0 承诺。

## 发布、更新与下线

用户可显式执行首次发布、更新和下线。成功发布生成稳定公开地址，应能在未登录、没有本地项目状态的浏览器中打开指定结果；下线后公开结果应不可访问，发布失败保留上一个线上版本。

以下保存规则适用于已发布且仍在线的项目，包括文件面板手工保存可发布源码、通过适用校验并形成新版本的情形。普通文档保存、首次发布、下线后重新发布、Restore 和无发布能力的源码版本不借此改变规则。**AI 修改自动形成版本是明确例外：无论选择哪种策略，都先预览，再由用户显式 Update；批准修改任务不等于批准上线。**确认依据为 [PQ-04](./产品澄清.md#pq-04)。

| 发布策略 | 保存新版本的影响 | 用户需要看到什么 |
| --- | --- | --- |
| 指定版本（Specify Version） | 保存不改变线上，显式 Update 后才更新 | 线上版本与当前编辑版本；不一致时提供明确更新入口 |
| 始终最新（Always Latest） | 上述显式保存会更新线上；AI 自动形成版本不触发 | 保存控件明确提示“保存并更新线上”；AI 修改结果另显示预览和 Update 入口 |

支持公开卡片的标题、描述和封面，以及 Public、Link Only 两种分享方式；V1 不承诺带成员授权的 Private 发布。Agent 不能自行选择或改变发布决定。Always Latest 覆盖的显式保存不要求再点 Publish；AI 自动形成版本仍须用户预览后 Update。

这里的交付与部署指生成项目的可用产物和发布能力。平台自身如何部署仍由[运行与部署](../../../operations/01-运行与部署.md)维护；不存在匹配适配器时，不自动承诺任意项目或外部托管平台部署。
