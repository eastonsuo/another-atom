## PQ-01：选择“始终最新”后，保存源码文件要不要更新线上？

**当前效力：已被 [PQ-05](#pq-05) 替代。** 以下保留当时的条件、选择与确认，不再作为现行保存行为的依据。

### 问题来源与已有依据

确认前的基线 `d5a501b` 中，产品规则存在直接差异，以下保留问题产生时的依据：

- [Feature 05 产品说明](../../03-用户交互与协作/05-项目文本文件阅读与编辑/01-产品说明.md)第 6.2、6.3 节及第 7 节要求：源码保存产生新版本，但文件保存不自动改变线上版本。
- [版本预览与发布规则](./02-版本预览与发布规则.md)第 6.7 节和 [Feature 12 产品说明](./01-产品说明.md)“发布、更新与下线”要求：指定版本（Specify Version）下保存不更新线上；始终最新（Always Latest）下保存新版本会更新线上，并明确提示“保存并更新线上”。
- [Feature 03 产品说明](../../03-用户交互与协作/03-人工确认与流程恢复/01-产品说明.md)第 2.3 节允许已完整展示对象与后果的明确操作本身构成确认，不要求重复弹窗。因此，“需要显式确认”本身不能证明每次都必须再点一次 Publish。

代码仅用于说明当前条件：[文件保存接口](../../../../another_atom/api/routes.py)中的 `save_project_file_content` 仍拒绝受保护应用源码走普通文本保存；[文件分类](../../../../another_atom/repository/service.py)中的 `repository_file_capabilities` 将固定版本源码标为不可直接编辑；[当前发布界面](../../../../studio/src/App.tsx)中的发布调用固定传入 `specify_version`。这些现状不能决定未来源码文件保存应采用哪条产品规则，本轮也未执行发布验证。

### 为什么需要确认

设项目已经发布，用户已经选择“始终最新”，随后在文件面板修改 CSS 并成功保存为新版本：当时两份规则会分别得出“线上不变”和“线上更新”，且没有说明文件面板是发布策略的例外。

本问题只讨论**已发布项目、仍处于发布状态、保存可发布源码且通过适用校验并形成新版本**的情形。普通文档保存、首次发布、已下线项目重新发布，以及没有发布能力的源码版本不借此扩展承诺。历史版本恢复（Restore）已有“不自动发布”的单独规则，本项不将它改成普通保存。

### 需要确认的选择

| 选择 | 用户实际得到的行为 | 优势与代价 |
| --- | --- | --- |
| A：文件保存遵循发布策略 | 指定版本下只保存；始终最新下保存并更新线上，保存操作明确说明线上影响 | 发布策略在该入口仍然有效；代价是用户保存源码就可能影响线上，不能只显示普通“保存” |
| B：文件保存是明确例外 | 无论选择哪种策略，文件面板只保存新版本，用户另行执行 Update 才改变线上 | 文件编辑与线上更新分开；代价是“始终最新”不覆盖该入口，必须解释例外并修订全局表述 |

**当时建议 A，并获用户确认。** 它沿用已有发布策略的含义，不因编辑入口不同而改变“始终最新”的结果。前提是保存前明确显示线上影响，未通过校验不形成新版本，更新失败不能破坏原线上版本。该确认不等于授权 Agent 自行发布。

**当时的归一化产品结论（已被替代）**：选择 A。文件面板手工保存可发布源码，通过适用校验并形成新版本后遵循用户已选择的发布策略：指定版本只保存，另行 Update 才更新线上；已发布且仍在线的始终最新项目保存并更新线上，按钮明确写成“保存并更新线上”。校验失败不形成新版本，更新失败保留原线上版本。普通文档保存、首次发布、下线后重新发布、Restore 和无发布能力的源码版本不借此改变规则。AI 自动形成版本的独立结论见 PQ-04，不从本项推定。

## PQ-04：AI 修改成功后自动形成新版本，也应该跟随“始终最新”更新线上吗？

### 问题来源与范围

迁移前 `b3da451` 的统一 Chat 文档第 8 条验收要求“批准后的修改成功才创建新版本，且不改变线上发布指针”；[对话衔接文档](../../03-用户交互与协作/01-项目对话与交互控制/02-统一对话与流程衔接.md)曾将该冲突指向本问题。本 Feature 的[发布规则](./02-版本预览与发布规则.md)原有一般规则要求 Always Latest 在保存新版本后更新线上，未说明 AI 自动形成版本是否等价于用户的保存操作。以下保留当时的选择，现行规则已按本次答复回写。

这里仅讨论：项目已经发布且选择 Always Latest，用户批准了一次代码修改，AI 执行与校验成功并形成新版本。它不等于 PQ-01 的用户手动保存文件；修改任务的批准也未必已经完整展示了上线后果。首次发布、下线后重新发布、Restore 和无发布能力的源码版本仍不在本项内。

### 需要确认

| 选择 | 用户实际得到的行为 | 需要付出的代价 |
| --- | --- | --- |
| A：AI 修改也跟随 Always Latest | 成功生成可发布版本后更新线上 | 修改确认入口必须明确说明成功后的线上影响，不能让普通“修改代码”默默承担发布授权 |
| B：AI 修改只生成版本 | 先预览结果，用户另行 Update／保存发布后才更新线上 | 必须把 AI 自动生成版本说明为 Always Latest 的例外，避免“最新”含义不清 |

PQ-01 的手工保存确认不自动决定本项；本项现已由用户独立选择 B。

**回写范围**：本 Feature 发布规则和产品说明、Feature 01 的修改完成验收、Feature 04 的修改结果，以及相关确认规则与导航。AI 修改确认只批准代码修改，不批准自动上线；首次发布仍需明确用户操作，发布失败不能破坏原线上结果。

**用户原始回复**：

> 先预览再更新吧，有始终最新的选项吗？为啥会有这个

- 确认人：项目负责人（用户）。
- 确认日期：2026-09-29。
- 回复来源：本次对话对 PQ-04 的 A“AI 修改后自动更新线上”和 B“先生成版本，预览后再 Update”两种选择的直接答复。

**当时的归一化结论**：选择 B。AI 修改及适用校验成功后形成新版本，先供用户预览；只有用户显式执行 Update 才更新线上。即使项目选择 Always Latest，AI 自动形成版本也不触发上线。代码修改批准不等于发布批准；普通文档、首次发布、下线后重新发布、Restore 和无发布能力的源码版本不借此扩大范围。该结论已回写产品规则，不代表已实施或验证。

**当前状态**：先预览再手动更新的结论继续有效；PQ-05 已取消本功能的“始终最新”，不再需要为 AI 修改保留策略例外。

### 原始追问：“有始终最新的选项吗？为啥会有这个”

2026-09-29 基于代码基线 `ca9d774` 与 Git 历史核对，未访问部署环境、未重跑测试：

- 旧 PRD 在 2026-07-10 的提交 `de0fbdf` 中已包含 Always Latest 和 Specify Version 两种发布策略；仓库保存的 [Atoms 参考分析](../../../references/Atoms参考产品分析.md)也记录了两者。这只能证明旧材料已有该设计，不能据此证明 Another Atom 必须保留它，或推定用户当时选择它的原因。
- 该策略的设计作用是让线上跟随最新保存版本，省去逐次手动 Update；它不是版本记录或预览能力成立的必要条件。
- 当前[前端发布入口](../../../../studio/src/App.tsx)固定传入 `specify_version`，未提供策略选择控件。[后端发布与公开读取](../../../../another_atom/api/routes.py)接受并保存策略值，但公开内容读取显式发布的 `deployment.version_id`，并未按策略自动读取最新版本；[现有测试](../../../../tests/integration/test_repository_and_sandbox.py)的 `test_new_version_does_not_move_public_pointer_without_publish` 还明确要求 `always_latest` 下新增版本不改变线上指针。

因此，“旧设计有该选项”“代码有该枚举”“当前页面可选且自动更新已经可用”是不同事实。核对后向用户提出本功能取消该选项、同步替换 PQ-01 的建议，后续答复见 PQ-05。

## PQ-05：是否取消“始终最新”，统一先预览再手动发布／更新？

### 问题产生的条件

用户在 PQ-04 选择 AI 修改先预览再更新，同时追问“始终最新”的来源。现有证据表明它来自旧设计、不是当前界面已开放的选项。继续保留会形成“手工保存自动上线、AI 修改不自动上线”的两套入口规则；因此提出取消该选项，将保存版本与上线操作分开。

**向用户确认的具体问题**：是否把 V1 统一为“修改并保存 → 预览检查 → 主动发布／更新线上”，手工保存也不自动上线，并取消“始终最新”？这会同时替换此前以保留该选项为前提的手工保存规则。

**用户原始回复**：

> 对

- 确认人：项目负责人（用户）。
- 确认日期：2026-09-29。
- 回复来源：本次对话中，紧接上述取消选项、统一手动发布／更新建议的答复。

**归一化结论**：

1. 本功能不提供“始终最新”选项，也不需要让用户在两种发布策略之间选择。
2. 手工源码保存与 AI 修改经适用校验形成新版本后，只更新工作版本，供用户预览检查，不自动改变线上版本。保存、快捷键保存或批准代码修改均不构成上线操作。
3. 首次发布、下线后重新发布仍须用户显式执行 Publish；已在线项目须显式 Update 才更新线上。界面区分当前工作版本与线上版本，发布失败保留原线上版本。普通文档保存不创建应用版本，Restore 不自动发布，无匹配发布能力的源码版本不因此获得发布能力。
4. PQ-01 的条件规则被本项替代；PQ-04 的先预览再手动更新继续有效，但不再是某种策略的例外。旧设计和参考材料仅保留为历史来源。

**回写与剩余工作**：已更新本 Feature 的产品说明、发布规则、指针示意及关联 Feature 的保存、审批和验收要求。现有 API、持久化与导出中的策略字段是否保留、如何处理旧枚举和历史数据，仍需技术设计与 Code Spec 明确；取消产品选项不等于本轮已删除代码字段或完成兼容处理。普通文件面板的完整源码保存及实际环境验收也未完成。
