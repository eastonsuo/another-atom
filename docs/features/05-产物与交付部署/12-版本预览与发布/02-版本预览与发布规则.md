<a id="p-622-project-与服务端本地-git-仓库"></a>

## 6.2.2 Project 与服务端本地 Git 仓库

- 每个 Project 创建时自动绑定一个平台服务端 local Git repository，默认一对一。
- 仓库位于执行宿主机持久化磁盘，不是用户电脑目录，也不连接 GitHub/GitLab remote。
- 初始化、Build、Edit、Resolve、Restore 都留下 Git commit；ProjectVersion 显示对应短 commit SHA。
- Restore 创建新 commit 和新 ProjectVersion，不执行 history rewrite；删除 Project 需要二次确认并进入可恢复清理流程。
- Repository 状态至少包含 provisioning、ready、dirty、saving、failed；仓库未 ready 时不能打开 WebIDE 或创建 Build Job。
- V1 不提供 remote、push、pull、branch 管理、SSH key 或 GitHub OAuth。用户代码归属先通过 Project 内可追溯本地仓库成立，远端绑定另行设计。

<a id="p-64-app-viewer"></a>

## 6.4 App Viewer

- Build Job 进入队列后立即展示 Queued 状态、`jobs_ahead` 和 Cancel；没有稳定历史样本前不显示预计完成时间。
- 排队、开始构建、校验和完成/失败都通过持久化事件更新；用户提交后 2 秒内必须看到第一条状态事件。
- 长时间模型请求不能只保留角色级循环动画。中央状态、项目日志和 Run 日志消费同一组持久化子步骤；刷新或 SSE 重连后按事件恢复当前尝试和最近失败原因。
- 默认展示当前需求生成的真实 Web 应用，不使用静态截图，也不默认套用 Mono Market 或商品目录。
- 页面、入口和交互分别与产品规格（ProductSpec）、架构设计（ArchitectureDesign）和实际源码包（SourceBundle）对齐；游戏、工具、看板和目录使用同一网页运行时适配器（Web Runtime Adapter）运行，但不把通用源码契约（Contract）限定为三段网页字符串。
- 支持 Desktop/Mobile 两种固定预览尺寸，切换时工作区布局不跳动。
- 支持刷新预览和在新标签打开当前预览。
- 支持通过结构化 Edit 修改主要标题、正文和视觉 Token；高级源码修改由受限 Vim 承接。
- Console 展示 info/error 两类事件，可清空。
- 提供一个可复现的模拟错误，例如商品详情按钮路由失效；点击 Resolve 后恢复并形成修复记录。
- 结构化编辑面板（Edit Panel）修改受控源码文件；高级用户可以进入受限 Vim 网页集成开发环境（WebIDE）修改允许的源码文件。两种入口最终都必须经过同一保存版本（Save Version）、构建（Build）、测试（Test）、校验（Validation）和 Git 提交流程。

<a id="p-65-可视化编辑"></a>

## 6.5 可视化编辑

- 文本元素可编辑内容。
- 按钮和强调元素可修改预设颜色。
- 商品图可从内置素材库替换。
- 修改有 Apply/Cancel，不应输入即破坏当前版本。
- Apply 后预览立即更新，并把项目标记为“有未保存改动”。
- 第一版不做任意 DOM 操作、拖拽布局或自由上传图片裁切；源码编辑由独立 WebIDE 承担，不在可视化面板内嵌第二套文本编辑器。

<a id="p-66-版本与-remix"></a>

## 6.6 版本与 Remix

- 首次构建生成 Version 1。
- 每次明确保存生成新版本，并记录时间、摘要、来源和 Git commit SHA：Build/Edit/Resolve/Restore。
- 版本历史是 Project 级能力。Project 已有版本后，Studio 必须在右侧工具栏提供常驻“版本”入口，不能因最新 Run 正在执行、失败、等待输入或取消而隐藏；没有版本时入口保持可见但禁用，并说明原因。
- 可切换任意版本进行只读预览。
- Restore 把选定历史版本恢复为新的当前版本，不覆盖或删除原历史。
- 失败页同时提供 Retry 和“回到上个可用版本”。Retry 创建新 Run 并重新执行；后者从版本历史倒序查找候选，复用首个经当前 Runtime/Validator 重新执行仍通过的版本。两者不能互相替代。
- V1 的“可用版本”必须已有通过的 ValidationReport，并在恢复操作中重新通过当前 Runtime/Validator；只有通过后才创建来源为 `restore` 的递增 ProjectVersion 和 Git commit。该结论只覆盖当前已实现运行时能力，不等于 Railway 部署健康证明。
- Restore 创建项目版本号，但不自动执行公开发布（Publish），也不改变 Public Route 的版本指针。失败 Run 和原有版本继续保留。
- Remix 从选定版本创建新项目，保留来源关系，但后续修改互不影响。
- 刷新浏览器后，项目、版本和当前编辑状态不能丢失。
- ProjectVersion 与 Git commit 一一对应；版本历史不允许 force reset、rebase 或删除旧 commit。

<a id="p-67-发布与分享"></a>

## 6.7 发布与分享

保存版本与上线是两个独立操作。V1 不提供“始终最新”，也不提供两种发布策略的选择；手工源码保存与 AI 修改都遵循“形成新版本 → 预览检查 → 用户显式发布／更新”，依据为 [PQ-05（2026-09-29 已确认）](./产品澄清.md#pq-05)。

- 支持首次 Publish、Update 和 Unpublish。
- 发布成功后生成稳定公开 URL，并可复制和打开。
- 公开 URL 应在无登录、无本地项目状态的浏览器中访问，展示被发布版本。
- 手工源码保存和 AI 修改通过适用校验并形成新版本后，只更新当前工作版本，线上仍保持原版本。用户预览检查后显式 Update，才更新已有线上内容。
- 保存按钮和快捷键保存只负责保存，不合并上线；批准代码修改也不构成发布批准。用户明确执行 Publish、Update 或 Unpublish 时，应展示目标与后果，是否需要额外确认沿用 Feature 03，不重复增加弹窗。
- 发布面板持续显示 `线上版本 vX / 当前编辑 vY`；两者不一致时，Update 是将工作版本更新到线上的唯一入口。
- 普通文档保存不创建应用版本；首次发布、下线后重新发布须显式 Publish。Restore 不自动发布，无发布能力的源码版本不因保存而获得发布能力。
- 源码未通过适用校验时不形成新版本；发布或更新失败保留原线上版本。保存结果与上线结果分别展示，不能把“已保存”当成“已上线”。
- Share 支持 Public 和 Link Only；Private 不进入 V1.0，因为第一版没有公开应用访问控制与成员授权体系。
- 支持编辑公开卡片的标题、描述和封面。
- Export 导出版本化 JSON；静态代码 zip 不属于 P0。下方保留原有最小字段集，其中 `publication.strategy` 的保留与旧值兼容仍待技术设计核对；其他导出边界不变，不导出密钥、凭证、绝对存储路径、原始对话或内部配额流水。

```json
{
  "schema_version": "1.0",
  "exported_at": "2026-07-11T00:00:00Z",
  "project": {
    "id": "project_123",
    "name": "Mono Market",
    "product_type": "product_catalog"
  },
  "repository": {
    "provider": "local_git",
    "default_branch": "main",
    "head_commit_sha": "abc123..."
  },
  "blueprint": {},
  "architecture_spec": {},
  "app_spec": {},
  "current_version": {
    "id": "version_2",
    "number": 2,
    "source": "Build|Edit|Resolve|Restore",
    "created_at": "2026-07-11T00:00:00Z",
    "summary": "Updated hero copy",
    "git_commit_sha": "abc123..."
  },
  "versions": [],
  "publication": {
    "status": "unpublished|live|paused",
    "strategy": "specified",
    "version_id": "version_2",
    "url": "https://example.com/apps/project_123"
  },
  "attachments": [
    {
      "id": "attachment_1",
      "file_name": "reference.png",
      "mime_type": "image/png",
      "size_bytes": 1024
    }

```

上述示例只表达显式指定发布版本，不再承诺 `latest` 模式。现有 API、持久化和导出的策略字段是否保留、旧枚举如何兼容，须由技术设计与 Code Spec 明确；本次产品确认不等于已修改实际 Schema 或完成历史数据处理。

版本历史只有一份。保存新版本只移动工作版本，公开地址始终指向用户最后一次成功发布／更新的版本：

```text
版本历史：v1 → v2 → v3 → v4
               ↑         ↑
           线上版本    当前工作版本

保存 v4：工作版本变为 v4，线上仍为 v2。
预览检查 v4 后显式 Update 成功：线上变为 v4，公开地址不变。
Update 失败：线上仍为 v2。

Restore v1 创建 v5，不删除 v2—v4，也不自动更新线上。
Remix v2 创建另一个项目，版本历史独立。
```

<a id="p-93-发布状态"></a>

## 9.3 发布状态

- Unpublished -> Publishing -> Live -> Updating -> Live。
- Live 可进入 Unpublishing -> Paused。
- 发布失败保留上一个 Live 版本，不能把失败结果覆盖到公开地址。

<a id="p-122-公开-url-会提高实现成本但不能删除"></a>

## 12.2 公开 URL 会提高实现成本，但不能删除

部署 demo 本体只能证明页面能打开，不能证明“产物发布”闭环。公开版本必须能从干净浏览器访问，因此需要真实持久化和发布快照；具体实现以架构设计文档为准。

<a id="a-84-user-resolve-与真实-build-error"></a>

## 8.4 User Resolve 与真实 Build Error

```text
真实 Build Error
build.failed -> run.failed -> 用户 Retry Build

已成功构建后的应用问题
validation.issue_detected -> User Resolve
    -> RevisionSpec
    -> new BuildJob
    -> ProjectVersion(source=Resolve)
```

两条路径共用 Artifact、Event 和 Version 基础设施，但状态和文案不同。Resolve 处理已构建应用中的可定位问题，不能被包装成 Agent 自动修复了 Renderer、编译或资源错误；Build Worker 的工程恢复规则以 [V1 系统架构](../../../design/03-系统架构概览.md)为准。

## 保存与上线的确认边界

现行规则以 [PQ-05](./产品澄清.md#pq-05) 和第 6.7 节为准：手工源码保存、AI 修改和 Restore 都不自动发布。PQ-01 的旧条件规则已被替代，PQ-04 的先预览再手动更新结论继续有效。该产品确认不替代技术合同、Code Spec、实现和验证。

## 未定版的远端仓库方向

原 b3da451 整体定位第 4.3 节提出未来可连接用户 GitHub/GitLab remote，但自动镜像、手动 Push/Pull 或仅作为导出的具体方式未定。V1 仍为服务端本地项目 Git，不因迁移扩展外部代码托管授权或同步承诺。
